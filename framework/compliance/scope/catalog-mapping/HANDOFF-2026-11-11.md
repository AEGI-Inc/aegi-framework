통제별 사유는 `items-clean/iso-scope-1111.jsonl`.

판단 기준(11-11 사용자와 정함): **점검이 통제의 본뜻을 판정하는가, 아니면 우리가 볼 수 있는 조각에 맞춰 좁게 해석했는가.** 좁게 해석한 예와 결론:

- 8.32 변경 관리를 GitHub PR 승인으로 보는 것은 좁다. 본뜻은 모든 변경의 공식 절차라 제외. 8.25 도 같은 이유로 오후에 뺐다. 저장소 접근 점검은 8.4 에 남는다.
- 8.22 네트워크 분리를 IP 허용 목록으로 보는 것은 틀리다. IP 허용은 5.15. 제외.
- 6.7, 5.34 는 다른 통제의 점검(IP, DLP)을 다시 쓴 것이라 제외.
- 8.11 데이터 마스킹에 걸린 점검은 화면 표시 옵션이라 제외.
- 8.7 악성코드는 「SaaS 테넌트의 방어 설정(메일 첨부, 링크)」으로 범위를 밝히고 포함.

### ISMS-P, PIPA (11-11 확정, Claude 판정)

- 멘토 범위 밖: ISMS-P 1번, 3번 18 확인사항, PIPA 법, 시행령, 표준지침 35 조항.
- 본뜻 판정 제외: ISMS-P 20, PIPA 10. 좁게 해석한 예: 2.8.5-02 소스 분리 보관과 2.8.5-03 변경 이력을 브랜치 보호 규칙으로 본 것, 2.10.1-04 보안 정책 예외 절차를 스팸 필터 우회 설정으로 본 것, 2.1.3-02 자산 책임자 지정을 CODEOWNERS 로 본 것. 정기 검토(2.5.6-02, 2.10.1-05, 2.10.2-04)는 절차라 뺐다. ISO 에서 뺀 통제와 같은 내용(6.7 원격 근무, 5.3 직무 분리, 8.13 백업, 8.22 망 분리)은 ISMS-P, PIPA 에서도 뺐다.
- 범위 안 목록과 통제별 사유는 `docs/compliance-scope-final-20261111.md`.
- ISO 8.25 안전한 개발 생명주기: 브랜치 규칙 점검으로 판정하던 「좁은 해석」이라 11-11 오후 사용자 확인을 받아 제외로 바꿨다(오전에는 포함). ISMS-P 쪽 같은 내용(2.8.1, 2.8.2)은 SaaS 적용 판정에서 이미 빠져 있다.

### 멘토 회의(11-10) 컴플라이언스 요지

- ISMS-P 는 2번(보호대책)만, PIPA 는 안전성 확보조치 기준만. 고유식별정보, 민감정보 보호조치는 안전성 확보조치와 겹치니 따로 두지 않는다.
- 모든 SaaS, 특히 파일 형태 객체는 개인정보가 있다고 가정한다. 내용 스캔(DSPM)은 하지 않으며 우리 영역이 아니라고 말한다. 우리가 말하는 것은 「데이터를 담는 객체와 그 외부 공유, 노출 경로」다.
- 자산 식별은 SaaS 안의 객체가 아니라 SaaS 자체(테넌트, 연동 앱)를 자산으로 본다.
- 대상이 너무 넓다(예: 3.1.3 에 객체 318 개). 식별 규칙을 보여 주고, 사용자가 기준을 넣거나 정탐, 오탐을 표시해 대상이 줄어드는 「맥락 먹이기」가 필요하다. 예: 이름이 dev, test 로 시작하면 시험 자원(사용자가 켜는 규칙).
- 매핑을 어떻게 했냐는 질문에 「규칙으로 찾았다」고 답할 수 있어야 한다.
