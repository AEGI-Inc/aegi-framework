# 이 규칙을 어떻게 만들었나

연결 규칙을 만든 방법과 지킨 원칙을 적는다.

## 왜 필요한가

SaaS 마다 수집한 객체를 하나의 그래프로 이을 때, 같은 SaaS 안의 관계는 벤더 API 가 바로 알려 준다. **SaaS 사이의 연결**(예: Slack 명령이 Okta 작업을 부른다)은 양쪽 값을 비교해야 보인다. 그 비교를 무엇으로, 얼마나 확실하게 하는지 적은 기준이 이 규칙이다.

## 연결 방법 모으기

**나눈 단위.** SaaS 쌍마다 파일 하나로 나눴다. SaaS 가 밖의 서버와 이어지는 방법은 SaaS 마다 `<SaaS>-external.yaml` 에 둔다.

**방법 하나에 적는 것.** 어디서 알아보나(API 와 조건), 무엇이 같으면 이어진 것인가, 그 값을 못 읽으면 어느 화면을 보나, 실제로 쓰이면 남는 감사 로그, 근거 문서. 칸의 뜻은 [`rules/legend.yaml`](../rules/legend.yaml)에 모았다.

**근거의 세기.** "무엇이 같으면 이어진 것인가"에는 근거가 센 순서로 등급을 붙였다. 설정에 상대 ID 가 적혀 있는 것(`config_id`)이 가장 세고, 로그 시각만 맞는 것(`log_time`)이 가장 약하다. **센 근거로 이미 이어졌다고 판단해도 약한 근거를 빼지 않고 모두 적는다.** 설정을 못 읽는 환경에서는 약한 근거만으로 판단해야 하기 때문이다.

**벤더 문서 확인.**
- 근거 주소는 직접 열어 확인한 문서로 적었다.
- 검색 요약만 본 것과 끝내 확인 못 한 필드는 그렇게 표시했다.

**빠진 조합 찾기.** "주소를 설정해 보내는 곳"(웹훅, 슬래시 명령 등)과 "주소로 불리는 곳"(Okta Workflows, Apps Script 웹앱 등)을 짝지어 표로 그려 보며 빠진 조합을 찾아 방법으로 더했다.

## 지킨 원칙

- **규칙에는 특정 회사의 값을 넣지 않는다.** 다른 환경에도 그대로 쓸 수 있어야 한다.
- **모든 근거 등급을 적는다.** 센 근거로 확정돼도 약한 근거를 지우지 않는다.
- **확인 못 한 것은 그렇게 적는다.** 벤더 문서에 없는 값은 「문서에 없음」과 함께 어디서 어떻게 읽어 내는지를 적는다. 그럴듯하다는 이유로 단정하지 않는다.
- **빈칸에는 이유를 적는다.** 값이 없으면 왜 없는지와 어떻게 채우는지를 같이 적는다.
- **비밀값은 넣지 않는다.** 토큰, 웹훅 주소, client secret 은 처음부터 넣지 않는다. 주소 자체가 비밀인 값은 호스트와 sha256 지문만 남긴다.
