# 이 정답을 어떻게 만들었나

2026-10-03부터 2026-10-05까지 이 저장소의 규칙과 시험 환경 결과를 만든 순서다. 무엇을 했는지와 그때 정한 원칙을 적었다. 숫자는 각 단계를 마친 시점 기준이다.

## 한눈에

1. **왜 필요했나**: 대시보드가 SaaS 사이 선을 맞게 긋는지 채점할 기준이 없었다.
2. **연결 방법 모으기**: 벤더 문서에서 "두 SaaS가 이어지는 방법"과 "이어졌다는 것을 확인하는 값"을 모았다.
3. **시험 환경에 대 보기**: 수집한 원본 데이터와 로그로 실제 연결을 하나씩 확인했다.
4. **빈칸 채우기**: 데이터가 없어 확인 못 한 방법은 수집 권한을 열고, 시험용 연동을 일부러 만들어 다시 수집했다.
5. **대시보드와 맞춰 보기**: 대시보드 코드에 규칙을 넣고, 시험 환경 결과와 대시보드 결과를 연결마다 비교했다.
6. **규칙 다시 검토**: 87가지 방법을 처음부터 다시 보며 근거와 어긋난 것, 확인 안 된 것을 고쳤다.
7. **공개 정리**: 개인 정보를 가리고 내부 용어를 풀어 이 저장소에 올렸다.

## 1. 왜 필요했나

AEGI 대시보드는 SaaS마다 수집한 객체를 하나의 그래프로 잇는다. 같은 SaaS 안의 관계는 벤더 API가 바로 알려 주지만, **SaaS 사이의 연결**(예: Slack 명령이 Okta 작업을 부른다)은 양쪽 값을 비교해야 보인다. 그런데 대시보드가 그 비교를 맞게 했는지 잴 기준이 없었다.

팀에 이미 있던 정답 파일은 "벤더가 직접 알려 준 연결"만 관계로 인정하고, 이름이나 로그로만 이어지는 것은 참고 기록으로 돌리는 규칙이었다. 이 규칙은 그대로 따르되, 그 사이에 있는 연결들을 **무엇으로, 얼마나 확실하게** 확인하는지까지 적은 기준을 따로 만들기로 했다.

## 2. 연결 방법 모으기

**나눈 단위.** 네 SaaS의 쌍 6개(Okta–GitHub, Okta–GWS 등)와, SaaS마다 밖의 서버와 이어지는 것 4개로 모두 10개 파일로 나눴다.

**방법 하나에 적는 것.** 어디서 알아보나(API와 조건), 무엇이 같으면 이어진 것인가, 그 값을 못 읽으면 어느 화면을 보나, 실제로 쓰이면 남는 감사 로그, 근거 문서. 칸의 뜻은 [`connection-rules/legend.yaml`](../connection-rules/legend.yaml)에 모았다.

**근거의 세기.** "무엇이 같으면 이어진 것인가"에는 근거가 센 순서로 등급을 붙였다. 설정에 상대 ID가 적혀 있는 것(`config_id`)이 가장 세고, 로그 시각만 맞는 것(`log_time`)이 가장 약하다. **센 근거로 이미 이어졌다고 판단해도 약한 근거를 빼지 않고 모두 적는다.** 설정을 못 읽는 다른 환경에서는 약한 근거만으로 판단해야 하기 때문이다.

**벤더 문서 확인.**
- 처음 목록 일부는 보조 AI가 연 문서를 기준으로 만들었다. 2026-10-04에 그 문서를 모두 직접 다시 열어 근거 주소를 고쳤다.
- 검색 요약만 본 것과 끝내 확인 못 한 필드는 그렇게 표시해 두었다.
- 다시 확인하며 바뀐 예: GitHub EMU의 OIDC SSO는 Entra ID 전용이라 Okta 방법에서 뺐다. Slack SAML은 Business+ 이상 플랜에서만 된다. Slack 워크플로 빌더에 GitHub 커넥터가 있어 방법을 하나 더했다.

**빠진 조합 찾기 (2026-10-05).** "주소를 설정해 보내는 곳"(웹훅, 슬래시 명령 등)과 "주소로 불리는 곳"(Okta Workflows, Apps Script 웹앱 등)을 짝지어 표로 그려 보니 빠진 조합이 9개 나왔다. 이것과 Slack → Okta Workflows 직접 호출을 더해 방법은 **87가지**가 됐다.

## 3. 시험 환경에 대 보기

**자료.** 팀 시험 환경의 수집 원본(2026-09-30~10-02), 그 원본으로 만든 대시보드 데이터, 팀이 만든 시나리오 서버의 기록, 예전 환경의 감사 로그(2026-09-17~09-30).

**적는 법.** 쌍마다 결과 파일을 하나씩 두고 세 부분으로 나눴다.
- **찾은 연결**: 양쪽 객체와, 등급마다 실제로 본 값과 그 값이 나온 수집 호출
- **쓰지 않는 방법**: 확인했더니 없는 것과 그 이유
- **빈칸**: 아직 못 본 값과, 어느 계정이 어느 API나 화면에서 보면 되는지

**판정 값.** `connected`(이어져 있음), `config_only`(설정만 있음), `outside`(상대가 예전 환경), `not_used`, `not_seen`, `unknown` 여섯 가지로 나눴다. 뜻은 [README](../README.md) 「시험 환경 결과 읽는 법」.

**검증.**
- 결과 파일에 적은 주장 95건을 수집 원본, 시나리오 서버 기록, 감사 로그와 스크립트로 다시 맞춰 모두 맞았다.
- 찾은 연결마다 규칙이 요구한 근거 칸 82개 중 65개는 값이 있고, 17개는 못 본 이유와 확인 방법을 적었다. 이유 없이 빈 칸은 없다.
- 관리 화면에서 눈으로 본 값은 화면 확인 기록으로만 두고 스크립트 대조에는 넣지 않았다.

**팀 정답과 대조.** 팀 정답 파일과 객체 표기(`provider:type:key=value`)를 맞추고, 두 정답이 다르게 말하는 곳을 따로 정리했다.

## 4. 빈칸 채우기

시험 환경에 해당 연동이 없어서 규칙을 실제 데이터로 확인할 수 없는 방법이 많았다. 두 가지로 채웠다.

**수집 권한 열기.** Okta 수집 앱의 API 권한, GitHub 소유자 토큰, Google Workspace 위임 범위 등 수집기가 읽지 못하던 값을 읽을 수 있게 했다. 관리 콘솔 작업은 사람이 하고, 순서는 콘솔별로 문서로 만들어 넘겼다.

**시험용 연동 만들기 (2026-10-05).** 규칙을 확인하려고 실제 연동을 일부러 만들었다.
- "ok"만 돌려주는 Okta Workflows 흐름과 Apps Script 웹앱을 만들었다.
- Slack 슬래시 명령 두 개와 GitHub 웹훅 하나가 그것을 부르게 했다.
- Okta Workflows의 Google Workspace 연결도 하나 만들었다.
- 공유 SaaS에 무엇을 만들기 전에는 내용을 보여 주고 승인을 받았다.

**다시 수집.** 팀 수집 저장소와 같은 구조로 우리 수집 저장소를 따로 두고, 팀 설정 파일은 고치지 않은 채 우리 자격 증명만 덧씌우는 옵션을 수집기에 더해 수집했다. 수집 결과마다 새 연결이 대시보드에 선이나 근거로 생기는지 확인했다.

**그 과정에서 찾은 문제.**
- 수집기가 GitHub 감사 로그와 Slack 앱 설정에 들어 있는 토큰을 원본 그대로 저장하고 있었다. 수집기가 그 값을 가리도록 고치고, 이미 저장된 원본 4개를 정리했다. 정리 전후 대시보드 데이터가 같은 것을 확인했다.
- 대시보드 정규화의 버그 셋을 테스트부터 써서 고쳤다. 같은 연결이 두 근거로 잡히면 센 근거를 버리던 것, 0건으로 끝난 부분 수집이 이전 토큰을 지우던 것, Okta Workflows의 Google 연결을 다른 앱으로 잘못 분류하던 것이다.

## 5. 대시보드와 맞춰 보기

**대조.** 2026-10-04 기준 대시보드 코드(main `d646b66`)의 수집 호출과 정규화 코드를 방법마다 맞춰 봤다. 당시 77가지 중 구현 17, 일부 구현 17, 지금 수집으로 구현 가능 20, 수집 추가 필요 22, 같은 값 없음 1이었다.

**구현.** 팀 저장소는 건드리지 않고 로컬 브랜치에서 구현 가능한 방법과 수집 호출 16개를 더했다. 87가지 기준으로 지금 데이터로 구현 54, 다음 수집부터 값이 들어옴 11, 수집 권한을 더해야 함 17, 수집 추가 필요 2, 일부 구현 2, 같은 값 없음 1이 됐다.

**비교 명령.** 시험 환경 결과와 대시보드 결과를 연결마다 비교하는 명령(옛 aegi-dashboard 의 `npm run gt:conn`. 지금 세 저장소에는 없다)을 만들었다. 정답의 근거 등급에 따라 대시보드가 그 연결을 어디에 둬야 하는지(선, 같은 사람 연결, 근거)를 정하고, 실제로 둔 자리와 비교한다. 2026-10-05 결과는 시험 환경 연결 47건 중 맞음 12, 약함 2, 없음 3, 환경 밖 7, 참고 23이다.

## 6. 규칙 다시 검토

87가지를 처음부터 다시 읽었다.
- 실제 데이터나 벤더 문서와 어긋난 방법 6개를 고쳤다. 예: GitHub 엔터프라이즈 SAML을 쓰면 조직 단위 팀 동기화는 할 수 없다.
- "미확인" 표시가 있던 방법 29개를 문서와 관리 콘솔로 다시 확인해 13개로 줄였다. 남은 13개는 공개 API가 없거나(Okta Workflows 흐름 정의, Slack 워크플로 트리거 주소) 실제 연동을 만들어야만 알 수 있는 것이다.
- 확인하지 않은 화면 경로는 넣지 않았다. 넣었다가 확인이 안 되면 뺐다.

## 7. 공개 정리

2026-10-05에 이 저장소에 올렸다.
- 개인 메일 주소, 외부 IP, 로컬 사용자 이름은 가렸다.
- 비밀값(토큰, 웹훅 주소, client secret)은 처음부터 넣지 않았다. 주소 자체가 비밀인 값은 호스트와 sha256 지문만 남겼다.
- 팀 안에서만 쓰던 줄임말과 이름을 풀어 썼다. 수집 호출 번호(`GH-15` 등)는 출처를 가리키는 데 필요해서 남기고 README에 읽는 법을 적었다.

## 지키려고 한 원칙

- **규칙과 환경을 나눈다.** `connection-rules/`에는 특정 회사 값을 넣지 않아 다른 환경에도 그대로 쓴다. 우리 환경 값은 `test-environment/`에만 둔다.
- **모든 근거 등급을 적는다.** 센 근거로 확정돼도 약한 근거를 지우지 않는다.
- **확인 못 한 것은 그렇게 적는다.** 벤더 문서에 없는 값은 "문서에 없음"과 함께 어디서 어떻게 읽어 내는지를 적는다. 그럴듯하다는 이유로 단정하지 않는다. (2026-10-05 까지는 "미확인", "추정" 표시를 썼고, 2026-10-14 에 모두 이 방식으로 바꿨다.)
- **빈칸에는 이유를 적는다.** 값이 없으면 왜 없는지와 어떻게 채우는지를 같이 적는다.
- **공유 자원은 조심한다.** 팀 저장소와 팀 설정 파일은 고치지 않았다. 공유 SaaS에 만드는 것은 미리 승인을 받았다. 비밀번호 입력과 콘솔 로그인은 사람이 했다.
