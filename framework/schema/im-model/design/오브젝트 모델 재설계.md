
결국 오브젝트를 뽑는 과정:

재료(SaaS API/log docs) —가공 —> 오브젝트 카탈로그(해당 SaaS에 존재할 수 있는 모든 오브젝트)

팔란티어의 온톨로지에서는 오브젝트를 만드는 기준이 “필요하다”

우린 근데 뭐가 보안적으로 필요한 대상일지 알기가 어려움

어떤 원칙/규칙으로 보안적으로 의미있는 대상이라고 볼건지 애매함 → SaaS마다 다를수도 있음

그래서 선택한 접근이

1. 일단 넓게 오브젝트가 될만한 후보들을 뽑기(inventory) -> LLM이 판정
2. interface기준으로 판정하지(interface가 부여 가능하면 object로 판정) -> 이것도 LLM이 판정

지금 크게 문제가
1. 결정론적으로 오브젝트 추출이 가능해야되는데 지금은 LLM으로 블랙박스처럼 되어버리는게 너무 많음
2. 개별 SaaS에 반복적으로 적용가능해야하는데 지금은 LLM 프롬프트 방식이라 가능하지만 1번 문제를 해결하는 과정에서 범용성이 사라질 가능성이 높음
   
팔란티어의 원칙대로 필요에 의해서 오브젝트를 구성하면 SaaS를 전부 이해하지 못할수도 있음
대신 필요 없는 오브젝트들은 별로 안생김

뭐가 보안적으로 의미있는 오브젝트이지? -> 인터페이스 부여 가능 여부?

Tenant가 되게 애매하네
뭔가 집합 느낌인데
organization, enterprise, workspace, group -> policy를 적용 받을수 있는 대상이니까 오브젝트로 보는게 맞는것 같긴 한데


애초에 SaaS 별로 API docs, Log Docs의 형태나 구성이 다름
즉 AI를 이용해 scraping 하더라도 하나의 표준을 정해놓고 긁어야함

API의 경우는 request, response, scope등의 정보
Log의 경우 eventType, log field, 보존 기간 등
자연어 설명까지 알아서 붙이기

## 확정 (2026-10-12)

후보 추출 자료는 네 가지다.

1. API 명세: 요청과 응답 스키마 모두. 명세 안의 구멍(속성 없는 object, 문자열에 담긴 JSON, 예시에만 있는 필드, 열린 맵)은 그 구조를 정의한 외부 문서로 메운다
2. 감사 로그 카탈로그
3. 이벤트, 웹훅 카탈로그
4. 권한 어휘 카탈로그 (OAuth scope, 역할과 권한 목록)

플랫폼 동작 문서와 기준표는 후보 추출이 아니라 위협 판정 단계의 자료다. Object 쪽에서는 계약 필드 일부(Profile 상수)에만 쓴다.

같이 정한 것: 후보는 넓게 뽑고 판정에서 거른다. 판정은 Interface 9종을 구조 신호로 붙인다. `triggered_by` 끝점에 Resource, Integration을 더했다(aegi-schema 브랜치 `triggered-by-endpoints-1012`, PR 생성 대기).
