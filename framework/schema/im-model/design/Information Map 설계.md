# Information Map 설계: 사전 없이 (2026-10-15)

## 요약

- 사람이나 AI가 써 둔 대응표(사전)를 판정에서 모두 뺀다. 판정은 IR에 있는 근거와 모든 provider에 같게 적용되는 규칙으로만 한다.
- 사전에서 읽어도 되는 것은 변환 설정뿐이다: 자료 위치, 경로 접두사 벗기기.
- 공간(같은 대상들의 집합)은 키를 몰라도 만들 수 있다. 경로 위치와 모양의 왕복, 모양 같음으로 묶는다. 키(ID)는 그다음에 근거로 찾아 붙인다.
- 사전을 빼면 키 선언이 크게 줄어든다(2절). 빈 곳은 예시 인스턴스와 테넌트 실측(4순위)으로 메운다. 이것이 수집 단계로 돌아가는 가장 큰 되먹임이다.

## 1. 원칙

1. 판정 규칙은 provider 이름으로 갈라지지 않는다.
2. 근거는 IR 개체와 그 등급뿐이다: stated, transform, example, observed. curated 등급은 쓰지 않는다.
3. 이름은 판정에 쓰지 않는다. 쓰는 것은 같은 출처 안의 정확한 식별자 같음뿐이다. 예를 들어 `$ref` 스키마 이름이 같은지, 경로 템플릿이 같은지는 쓴다. 이름 조각(`repository_id`에서 `repository`), 접미사 목록(`*_id`), 동사 표, 래퍼 이름 표는 쓰지 않는다.
4. 근거가 없으면 「모름」으로 남기고 되먹임 대기열에 올린다. 그럴듯한 추정으로 채우지 않는다.
5. 공간 이름은 표시용 꼬리표다. 판정에 쓰지 않으므로 이름이 바뀌어도 결과가 바뀌지 않는다.

## 2. 사전을 뺀 결과 (새 IR, 2026-10-15)

| 뺀 것 | 쓰던 곳 | 대신 |
| --- | --- | --- |
| 이름 규약 키 (`record_key_fields`, `record_key_named_id`, `local_key_fields`) | 레코드 키 | 원문 키 선언과 인스턴스 근거(5절) |
| GitHub node_id 형식 | 타입 반대 근거, GraphQL 연결 | 결정 필요(7절) |
| Slack 추가 접두사 5개 | ID 형식 | 원문 `defs_*` 정의만 |
| 동사 표 (`verb_class`) | Slack RPC 동작 종류 | `unknown` (원문이 말하지 않음) |
| 래퍼 이름 표, 경로 낱말 `search` | REST 동작 종류 | 「배열 속성이 하나뿐인 객체」(구조) |
| `param_space`, `audit_alias`, `schema_space`, `field_space`, 감사 토큰 표 | 공간 합치기, 감사 연결 | 왕복, 모양 같음, 카탈로그 대상 선언, 실측 |

| provider | 키 선언 | 근거 |

## 3. 단계 A: 공간 만들기 (키 없이)

꼭짓점: 경로 위치(`orgs/{}/teams/{}`), 모양, ID 형식, GraphQL 타입.

간선 (강한 것부터 합친다):

| 간선 | 조건 | 등급 |
| --- | --- | --- |
| 단건 왕복 | 경로가 `…/{}`로 끝나는 read_one 동작의 응답 모양 = 그 위치 | transform (동작 종류가 transform) |
| 목록 왕복 | read_many 동작의 원소 모양 = 같은 컬렉션의 단건 위치 | transform |
| 모양 같음 | 같은 출처에서 `$ref` 이름이 같음. 인라인은 속성 이름과 타입 집합이 정확히 같고 속성 수가 기준 이상 | stated, 구조 |
| 다형 하위 유형 | 원문 판별자가 하위 유형을 말함(`alt_kind: subtype`) | stated |
| 원문 바인딩 | 파라미터가 어느 모양의 키를 받는다고 원문이 말함 | stated |
| ID 형식 | 같은 원문 ID 형식이 붙은 자리 | stated |
| 실측 값 같음 | 테넌트 값에서 한 위치에 넣은 값이 한 모양의 레코드를 연다 | observed |

반대 근거 (합치지 않는다):
- 각자 단건 조회 위치를 가진 두 동치류는 약한 간선(다형 대안, 예시)으로 합치지 않는다.
- 원문 판별자나 GraphQL union이 서로 다른 대상이라고 말한 대안(`alt_kind: distinct`)은 합치지 않는다.

키 없이 묶이는 이유: GitHub `/users/{username}` 왕복은 「그 위치에 넣은 값이 `public-user` 하나를 연다」는 사실만으로 그 위치와 모양을 같은 집합으로 묶는다. 어느 필드가 그 값인지는 몰라도 된다.

## 4. 단계 B: 정보를 ID와 속성으로 나누기

모든 값 자리(모양을 용기별로 펼친 것)를 셋으로 나눈다.

| 분류 | 근거 |
| --- | --- |
| ID | 원문 타입(`ID`, Salesforce `id`와 `reference`), 원문 ID 형식, 원문 참조 선언, 경로와 인자 파라미터, 인스턴스 값이 다른 동작의 경로 위치에 들어감, 인스턴스 값이 다른 레코드의 키 값과 같음(희귀 값), 값이 동작 경로 템플릿에 맞는 URL |
| 속성 | 원문 타입이 boolean, 시각, 고정 enum. 위 ID 근거가 없는 자리 |
| 미정 | ID처럼 보이지만(이름만) 근거가 없음. 이름은 보지 않으므로 실제로는 「속성」과 같이 다루되, 수집 되먹임 목록에 따로 센다 |

미정을 세는 데도 이름 접미사를 쓰지 않는다. 대신 문자열 또는 정수이면서, 값이 예시나 실측에서 레코드마다 다르고 여러 레코드에 되풀이되는 자리(값 분포 근거)만 센다. 예시가 없으면 세지 않는다.

ID 겸 속성(I1): `login`, `email`처럼 경로 위치에 들어가는 값은 ID(대체 키)이고 그 공간의 속성이기도 하다.
URL(I2): 값이 동작 경로 템플릿에 맞으면 ID(참조). 맞는 템플릿이 없으면 속성.

## 5. 단계 C: ID가 가리키는 대상

| ID 역할 | 대상 정하는 근거 |
| --- | --- |
| 자기 키 (기본) | 원문 키 선언. 없으면 인스턴스: 같은 레코드가 여러 동작과 출처에 나올 때 늘 같은 값을 가지는 필드, 그 값이 다른 레코드의 참조 값으로 나옴 |
| 주소 키 | 예시 왕복: 동작 예시 요청의 경로 값이 응답 인스턴스의 어느 필드 값과 같은가. 없으면 실측 |
| 참조 | 원문 참조 선언, 원문 ID 형식, 박힌 레코드(모양이 공간에 속함), 인스턴스 값 공출현, URL 템플릿 |
| 조합 키, 부모 안 키 | 경로 위치 순서(부모 위치 아래 단건 위치), 원문 ID 정의 |

대상을 못 정한 ID(I4)는 공간을 만들지 않는다. 담은 레코드의 정보 항목으로 남기고 「가리키는 대상 모름」을 달며, 참조와 relation에는 쓰지 않는다. 문제 기록에 무엇이 있으면 풀리는지 적는다.

## 6. 단계 D: 매핑

1. 모양을 용기(동작 응답, 요청, 이벤트 payload, 감사 payload, 인스턴스)별로 펼친다.
2. 값 자리마다 가장 가까운 바깥 레코드 출현을 찾는다. 레코드 출현은 「그 모양이 단계 A에서 공간에 속한다」로 정한다. 키를 몰라도 된다.
3. 결정자:
   - 레코드가 자기 공간을 가지면 그 공간이다. 그 자리는 오브젝트 속성이다.
   - 자기 공간이 없고, 서로 다른 공간을 가리키는 ID 자리가 둘 이상이면 ID×ID 공간이다. 경로가 두 공간 위치로만 정해지는 단건 위치도 그렇다. 그 자리는 relation 속성이다.
   - 바깥 레코드가 없으면 그 동작 하나가 결정자이고, 문제로 남긴다.
4. 정보 항목은 (결정자, 레코드 안 상대 경로)다. 같은 공간의 다른 모양에 같은 상대 경로가 있으면 같은 항목이다(같은 출처 안 정확한 같음).
5. 항목에 붙이는 것:
   - 읽는 동작과 권한
   - 쓰는 동작: 요청 경로 = 응답 경로
   - 거르는 동작: 원문 바인딩이 있을 때만
   - 바꾸는 감사 action: 카탈로그 대상 선언이나 실측 값 같음
   - 출처 등급

## 8. 결정과 첫 실측 근거 (2026-10-15)

M1~M4는 권고대로 정했다.

- M1: 새 IR에 node_id 형식이 없다. 옛 v2(`info_map_v2.py`)의 해독 코드는 비교용으로 남아 있고 새 판정에는 쓰지 않는다
- M2: Slack LLM 정리본 예시를 뺐다(`norm_slack.py`가 `md_examples`를 부르지 않는다). 예시 값 6개, 응답 자리 21개, 인자 6개가 줄었다
- M3: 감사 연결은 원문 대상 선언과 실측만 쓴다
- M4: 이미 받아 둔 테넌트 응답 중 요청 경로 기록(`_log.tsv`)이 있는 것을 실측 인스턴스로 넣었다(`ir2/tenant_log.py`). GitHub 39개(`lab_0926`), Okta 129개(평가판 둘, 세 묶음). 요청 경로를 동작 경로 틀에 맞춰 경로 값을 `instance.ext.request.params`에 남긴다. 맞지 않은 파일은 없었다

경로 값이 응답의 어느 필드 값과 같은가 (이름을 보지 않고 값만 비교):

| provider | 경로 파라미터 | 같은 값이 나온 응답 필드 | 횟수 |
| --- | --- | --- | --- |
| GitHub | `org`, `owner` | `login` | 18, 21 |
| GitHub | `repo` | `name` | 21 |
| GitHub | `team_slug` | `name`, `slug` (값이 같아 둘 다) | 12 |
| Okta | `appId`, `groupId`, `policyId` | `id` | 34, 6, 31 |
| Okta | `id` (사용자) | `id`, `externalId` (값이 같아 둘 다) | 16 |

이것이 사전 없이 주소 키를 정하는 실측 근거다. GitHub 조직과 저장소의 주소 키가 `id`가 아니라 `login`, `name`이라는 것이 값으로 나왔다. `team_slug`처럼 두 필드 값이 같은 테넌트에서는 한쪽으로 정해지지 않는다. 두 값이 다른 레코드가 있는 테넌트 자료가 더 필요하다(되먹임: 수집).

아직 넣지 않은 테넌트 자료: `okta/trial-5102035/group_cycle_0927`, `cross/okta_slack_idp_0927`, `slack_v2`. 요청 경로 기록이 없거나 형식이 달라 따로 맞춰야 한다.

### 9.1 루프마다 찾은 오류와 고친 곳

| 루프 | 찾은 것 | 원인 단계 | 고침 |
| --- | --- | --- | --- |
| 1 | `GET /repos/{owner}/{repo}`가 목록 조회로 분류 | 정규화 | 경로 끝 위치가 하나를 고르면 단건 조회가 먼저. 목록 래퍼는 「객체 원소 배열 속성이 하나뿐인 객체」 |
| 1 | 실측 왕복 주소 키 0 | 규칙 | 같은 응답 안이 아니라 모든 실측 응답에서 경로 값을 찾는다. 관측마다 맞은 속성 집합의 교집합이 하나일 때만 정한다 |
| 2 | 문서 예시끼리 값이 같아 생긴 참조가 「실측」 등급 | 규칙 | 양쪽이 모두 실측일 때만 observed, 아니면 example |
| 2 | Okta `_links` 안의 링크까지 세어 relation 과다 | 규칙 | relation 근거는 레코드 바로 아래 자리만 |
| 3 | Salesforce 1,718개 sObject가 공간 하나로 뭉침 | 규칙 | 같은 경로(`GET /query`)가 서로 다른 원소 모양을 돌려주면 한 컬렉션이 아니다. 그 목록 왕복은 약한 간선 |
| 3 | GitHub GraphQL 타입 290개가 공간 12개로 (구조가 같은 다른 이벤트 타입) | 규칙 | 원문이 각자 키를 선언한 모양끼리는 약한 간선(지문)으로 합치지 않는다 |
| 3 | 박힌 레코드(Slack 응답 안 `user`)의 속성이 매핑되지 않음 | 규칙 | 박힌 공간 레코드도 그 공간에 놓는다 |
| 3 | 고아를 동작마다 따로 세어 Confluence 1만 8천 항목 | 규칙 | 고아는 뿌리 모양 단위로 모은다 |
| 4 | GitHub 감사 action마다 따로인 예시 모양이 고아로 9만 항목 | 규칙 | 감사, 이벤트 항목은 이벤트 레코드다. 결정자 `catalog:<종류>:<출처>`로 모은다 |
| 4 | Slack RPC 응답의 `ok`, `response_metadata` 가 고아 | 규칙 | 응답 봉투: 같은 출처 고아 뿌리 모양의 30% 이상에 되풀이되는 자리 (이름 같음 사용, 검증 대상) |
| 4 | 원문 참조(Salesforce Refers To)가 참조 간선에 빠짐 | 규칙 | ID 자리 참조도 센다. Salesforce 참조 0 → 3,150 |
| 5 | `GET /user`처럼 객체 하나를 돌려주는 조회를 목록 래퍼로 보아 속성을 버림 | 규칙 | 원소가 공간에 속하고 뿌리는 공간이 아닐 때만 목록 래퍼로 본다 |

### 9.3 고아 정보 처리 (지금까지 찾은 방법)

고아는 「어느 공간에도 기대지 못한 값」이다. 사유별로 다르게 다룬다.

| 사유 | 예 | 처리 |
| --- | --- | --- |
| 이벤트 레코드 | 감사 로그 항목, 이벤트 payload | 고아가 아니다. 이벤트 결정자로 모은다. 대상 ID는 실측으로 공간에 잇는다 |
| 응답 봉투 | `ok`, `response_metadata`, 페이지 정보 | 정보 지도에서 뺀다. 검증 보고에 수를 남긴다 |
| 경로 맥락 | `GET /orgs/{org}/actions/permissions` 처럼 키 없는 설정 객체 | 그 응답을 고른 경로 끝 위치의 공간 속성(구조 근거) |
| relation | 자기 공간 없이 서로 다른 공간 둘 이상을 가리키는 레코드 | ID×ID 결정자 |
| 위치 없음 (RPC, 액션 응답) | Slack 메서드 응답, POST 액션 결과 | 정규화 되먹임: 인자의 원문 ID 정의를 IR에 옮기면 맥락 공간이 정해진다 |
| 위치가 공간이 아님 | Confluence v1 `Content` (단건 조회 폐지) | 수집 되먹임: 실측으로 v1 id와 v2 id 같음 확인 |
| 나머지 | 근거가 없음 | 뿌리 모양 단위로 묶어 남기고 되먹임 대기열 |

### 9.4 이름 같음을 쓰는 규칙과 검증

원칙은 이름 비교를 피하는 것이다. 피할 수 없이 쓰는 곳은 셋이고, 모두 다른 근거와 대조한 수를 `metrics.json`의 `verify`에 남긴다.

| 규칙 | 이름을 쓰는 곳 | 검증 |
| --- | --- | --- |
| 같은 모양 지문 | 속성 이름과 타입 집합 같음(같은 출처, 6개 이상) | 약한 간선. 단건 위치가 다르거나 원문 키 선언이 다르면 합치지 않는다. 합친 수와 막힌 수를 센다 (GitHub 1,210 중 77 합침, 19 막힘) |
| URL 경로 틀 | URL 경로 조각과 동작 경로 틀의 글자 조각 같음 | 사용 수를 센다. 다음 루프: 실측 URL의 경로 값이 대상 레코드의 주소 키 값과 같은지 대조 |
| 응답 봉투 | 같은 출처 여러 뿌리에 같은 이름 자리 | 옮긴 수를 센다. 다음 루프: 봉투로 옮긴 자리가 공간 레코드 안에도 나오면 되돌린다 |

### 9.11 루프 15: 중복 (2026-10-16)

같은 대상이 공간 둘로 갈라진 경우를 찾았다. 후보는 약한 근거(값 쌍, 지문, 다형 대안, 단일 자원)가 같은 대상이라는데 반대 근거(각자 단건 위치, 원문 키)에 막힌 쌍이다.

막힌 이유는 셋이다.

| 경우 | 예 | 판정 |
| --- | --- | --- |
| 같은 대상을 다른 열쇠로 여는 위치 (대체 키) | GitHub `user/{account_id}`(숫자 id)와 `users/{username}`(login) | 같은 대상. 실측으로 닫는다 |

| 다른 대상인데 예시 값이 복사됨 | `organization-full`과 `simple-user`, `issue`와 `pull-request`, 조직 팀과 엔터프라이즈 팀 | 다른 대상. 막는 것이 맞다 |

셋째 때문에 기준을 낮춰 합치지 않는다. 대신 중복 후보를 `info_map.json`의 `duplicate_candidates`와 문제 `duplicate_space_candidate`(되먹임: 수집, 실측)로 남긴다. 정체성을 말하는 근거만 센다. 생성과 수정 응답(작업 상태일 수 있다), 원소가 여럿인 목록 경로(이미 컬렉션이 아님)는 뺀다. 처음에는 이것을 빼지 않아 Salesforce 후보가 2,798쌍(`GET /query`), Google 9쌍(작업 상태 `Operation`)이 잡음으로 나왔다.

## 10. Jev 시범 (2026-10-16)

규칙이 「모름」으로 남긴 대기열을 Jev(TypeSafe System One, `jev-1.13.0`)로 채점했다. 코드 `ir2/jev_judge.py`, 캐시 `out2/<p>/map/jev_cache.jsonl`, 결과 `jev_duplicates.json`, 정답표 `ir2/eval/github_duplicates_gold.json`(Claude 제안, 사용자 확인 전).

원칙:

- 결과는 근거 등급 `model`이다. 원문, 구조, 실측 근거를 덮어쓰지 않고 공간을 자동으로 합치지 않는다
- 같은 입력이면 같은 결과: (모델, state, 질문)의 sha256으로 응답을 캐시한다
- 공개 명세에서 나온 이름, 속성, 경로만 보낸다. 테넌트 실측 값은 보내지 않는다
- 키는 `setup-output/secrets/jev.txt` 또는 환경 변수에서 읽고 출력하지 않는다

### 10.1 Jev 판정 형식 (2026-10-16)

조사한 지침(TypeSafe 문서를 옮긴 promptfoo, 정리 글 여러 편)과 1차 시범에서 배운 것을 형식으로 묶었다. 코드 `ir2/jev_tasks.py`(과제 정의), `ir2/jev_judge.py`(보내기, 캐시, 평가).

**과제 하나의 꼴**

```
과제 = {
  state:      판단에 필요한 것만 담은 JSON (공개 명세의 이름, 속성, 경로. 테넌트 실측 값 제외)
  questions:  원자 진술문 여럿 (한 요청에 함께, 같은 state 에 병렬 평가)
  combine:    진술들의 확률을 코드가 합치는 규칙
  thresholds: 결과별 기준 확률 (후보 표시, 규칙 근거와 함께 합치기). 정답표로 보정
  model:      고정 판 (jev-1.13.0)
}
```

**질문 쓰는 규칙**

| 규칙 | 이유 |
| --- | --- |
| Noul은 질문이 아니라 진술문으로 쓴다 | 문서 지침. 진술의 참 확률을 돌려준다 |
| 부정을 쓰지 않는다. 경계 사례는 `criteria`의 `true`, `false`에 적는다 | 부정은 정확도를 떨어뜨린다 |
| 판단 하나를 원자 진술 여럿으로 나눈다 | 요인이 섞이면 확률이 흐려진다. 같은 state에 질문을 더해도 비용, 시간이 거의 늘지 않는다 |
| 0.5는 「중간」이 아니라 「모름」이다 | 문서 지침 |
| `criteria` 예시는 평가 대상과 겹치지 않는 다른 분야에서 고른다 | 1차 형식 2에서 평가 쌍을 예시로 적어 점수가 부풀 수 있었다. 바꿔도 결과는 유지됐다 |
| 계산, 세기, 날짜 비교는 코드가 한다 | 1.13 판의 알려진 약점 |
| Noul과 Choice를 같은 판단에 섞지 않는다 | 형식에 따라 확률이 달라진다 |
| 영어로 쓴다 | 한국어는 확신이 크게 떨어진다고 알려져 있다 |

**중복 공간 과제의 진술**

| 진술 | 쓰임 |
| --- | --- |
| `same_entity`: A와 B는 같은 종류의 실제 대상을 기술한다 | 같은 대상 |
| `same_identifier`: A 레코드와 B 레코드는 같은 id 값으로 식별된다 | 같은 열쇠 |
| `variant_of_parent`: A와 B는 더 넓은 개념의 서로 다른 하위 유형이다 | 반대 근거 (구조만 같은 이벤트, 값 타입) |
| `scoped_view`: 한쪽은 다른 쪽과 같은 대상을 부모 맥락 안에서 보인 것이다 | 범위 보기 (팀 안의 저장소) |

합치기(코드): `(same_entity × same_identifier × (1 − variant_of_parent))`의 세제곱근.

**결과 (GitHub 중복 후보 27쌍, 같음 6)**

| 형식 | AUC | 기준 0.5 | 기준 0.6 |
| --- | --- | --- | --- |
| 1차: 질문 하나 | 0.921 | (0.5 기준 잘못 같음 4) | |
| 2차: 진술 넷 + 합치기 | 0.984 | 맞게 같음 5, 잘못 같음 0, 놓침 1 | 4, 0, 2 |

진술별 AUC: `variant_of_parent` 0.984(반대로 읽음), `same_entity` 0.956, `scoped_view` 0.948, `same_identifier` 0.885. 「하위 유형인가」가 가장 잘 가른다. 1차 질문 하나가 놓치던 구조만 같은 이벤트, 값 타입을 이 진술이 0.9 이상으로 잡는다. 놓친 하나는 README(`content-file`)와 `contents`다.

**쓰는 법 (권고)**

- 규칙 근거(값 쌍, 지문)가 있고 합친 점수가 기준 이상이면 「같은 대상 후보, 모델 확인」으로 표시한다. 합치기는 정답표가 커지고 provider 둘 이상에서 기준이 유지된 뒤에 연다
- 합친 점수가 낮고 `variant_of_parent`가 높으면 지문 간선을 끊는 반대 근거로 쓴다(등급 model)
- 모든 응답은 캐시하고 질문 형식이 바뀌면 새 키로 다시 채점한다. 비교 결과를 남긴다

**한계**

- 정답표 27쌍, provider 하나(GitHub), 정답표는 사용자 확인 전이다. 정답을 만든 쪽(Claude)과 Jev가 같은 쪽으로 틀렸을 수 있다
- 다음 과제의 형식: 이름만 있는 ID의 대상(Choice, 후보 공간 + `none`), 감사 action의 대상(Choice), 값 객체와 대상 구별(Noul 여럿). 같은 꼴로 `jev_tasks.py`에 더한다
