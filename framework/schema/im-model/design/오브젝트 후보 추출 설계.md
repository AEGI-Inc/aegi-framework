# 오브젝트 후보 추출 설계 (초안)

작성 2026-10-12. 「오브젝트 모델 재설계.md」의 확정 사항(자료 4종)을 이어받는다.

## 요약

```
① 수집      벤더 자료를 받아 고정한다 (원본 + 해시)
② 정리      네 종류의 공통 기록으로 바꾼다 (동작, 필드, 이벤트, 권한 어휘)
③ 필드 분류  필드마다 종류를 붙인다 (ID, 참조, URL, 비밀값 ...)
④ 후보 생성  규칙 E1~E7이 후보와 근거를 낸다
⑤ 합치기    같은 ID 공간이면 하나로 합친다
⑥ 폐포 검사  자료끼리 대조해 빠진 것을 대기열로 보낸다
```

- SaaS마다 다른 것은 ①의 가져오는 법과 ②의 변환기뿐이다. 변환기도 SaaS 단위가 아니라 **형식 단위**다(OpenAPI, Google Discovery, GraphQL SDL, Slack 메서드 문서, HTML 표).
- ③ 이후는 모든 SaaS에 같은 규칙과 같은 사전을 쓴다.
- **규칙은 자연어 설명(`description`)을 읽지 않는다.** 설명은 사람과 검토용으로만 남긴다.
- LLM은 ②에서 기계가 못 읽는 HTML을 표로 옮기는 초안 작성에만 쓴다. 그 결과는 공통 형식 검사와 사람 승인을 거친 뒤 고정 자료가 된다.

## 타입과 인스턴스

이 문서의 모든 단계는 **타입 수준**에서 돈다. 개별 대상(인스턴스)은 다루지 않는다.

| | 타입 수준 (이 문서) | 인스턴스 수준 (수집 이후) |
|---|---|---|
| 무엇 | 「이런 종류의 대상이 있다」 | 「이 대상이 있다」 |
| 단위 | 후보, ID 공간, 키 구성, 필드, 동작, 이벤트 종류, 권한 어휘 | ID 값, Object 행, 관계 행, 감사 로그 한 건 |
| 예 | Okta AppUser 후보, 키 구성 `[app_id, user_id]`, user 공간 | `(0oa2v0el…, 00ub0oNG…)` 배정 한 건 |
| 입력 | 벤더 자료 4종 (명세, 카탈로그, 명세 안의 예시 값) | 테넌트에서 받은 실제 응답 |
| 결과물 | 후보 카탈로그 → 판정 → Profile | Object, Relation, Link |

명세 안의 `example` 값과 ID 접두사 사전은 타입 수준 자료다. 테넌트에서 받은 실측 응답은 인스턴스 자료라 후보를 만들지 않고, 나중에 후보 카탈로그를 검증하는 데만 쓴다.

## 1. 수집

### 자료 위치

| 자료 | GitHub | Okta | Slack | Google Workspace |
|---|---|---|---|---|
| API 명세 | REST OpenAPI(`github/rest-api-description`, 로컬 있음), GraphQL SDL(로컬 `schema.docs.graphql`) | Management OpenAPI(`okta/okta-management-openapi-spec`). 거버넌스, PAM 등 제품별 명세 따로 | 기계용 명세 없음. 메서드 문서 페이지(로컬 캐시 121개), SCIM 문서(로컬) | API별 Discovery 문서(`directory_v1`, `cloudidentity v1`, `drive v3`, `gmail v1` ...) |
| 감사 로그 카탈로그 | 감사 로그 이벤트 문서 (기계용 데이터 파일 여부 확인 필요) | System Log 이벤트 유형 문서 (HTML) | Audit Logs API `actions`, `schemas` 응답 (로컬 문서 있음) | Reports API 애플리케이션별 이벤트 문서 (HTML) |
| 이벤트, 웹훅 카탈로그 | OpenAPI 3.1의 `webhooks` 절, 웹훅 문서(로컬) | Event Hook 대상 이벤트 표시(이벤트 유형 문서) | Events API 이벤트 유형 문서 | Workspace Events API 이벤트 유형, Drive/Gmail watch 문서 |
| 권한 어휘 카탈로그 | OAuth scope 문서, fine-grained 권한 문서, 조직 역할 API | OpenAPI의 동작별 `security` scope, 관리자 역할 권한 문서, 역할 API | scope 문서, 메서드 문서의 필요 scope | Discovery의 `auth.oauth2.scopes`와 메서드별 `scopes`, `privileges.list` API |

### 가져오는 법

| 형태 | 방법 | `extraction` 표시 |
|---|---|---|
| 기계용 명세 (OpenAPI, Discovery, SDL, JSON 응답) | 그대로 내려받는다 | `machine` |
| 구조가 일정한 HTML (Slack 메서드 페이지, 이벤트 유형 표) | 사이트별 고정 파서 | `parser@버전` |
| 구조가 일정하지 않은 HTML | LLM 초안 → 공통 형식 검사 → 사람 승인 | `llm_draft` + `approved_by` |

### 고정

```
sources/<provider>/<source_id>/
  raw/           받은 원본 그대로
  manifest.yaml  url, retrieved_at, sha256, 명세 버전, extraction
```

같은 `sha256`이면 다시 정리하지 않는다. 해시가 바뀌면 그 자료에서 나온 기록만 다시 만들고, 결과의 차이는 「어느 자료가 바뀌어서」로 설명된다.

## 2. 공통 형식

모든 기록은 JSONL 한 줄이다. 모든 기록에 `src`(자료 id, 원본 안 위치)가 붙는다.

### 2.1 operation — API 동작 하나

```yaml
op_id: okta.listApplicationUsers         # provider + 벤더가 준 id. 없으면 method+path
provider: okta
service: null                            # Object_Schema 의 service 규칙
surface: rest                            # rest | rpc | graphql | aip
http_method: GET
path: /api/v1/apps/{appId}/users         # rpc 는 메서드 이름, aip 는 flatPath
path_params: [appId]
verb_class: list                         # 아래 표, 결정론 계산
request_schema: null                     # schema_id
response_schema: okta.AppUser            # schema_id
record_path: "$[*]"                      # 목록 원소 위치. Slack 은 "$.channels[*]" 같은 것
scopes: [okta.apps.read]                 # 필요 scope
paging: link_header
deprecated: false
src: {source: okta-mgmt-2026.09, at: "paths./api/v1/apps/{appId}/users.get"}
```

`verb_class`는 이 순서로 정한다. 사전(`verb_lexicon`)은 버전 관리하는 자료다.

| 값 | REST | RPC (Slack) |
|---|---|---|
| list | GET이고 응답이 배열이거나 `record_path`가 배열 | 마지막 토큰이 `list`, `search` ... 이거나, 마지막 토큰이 동사가 아니고 응답이 배열 (`conversations.members`, `conversations.history`) |
| get | GET이고 응답이 하나 | `info`, `get`, `lookup`, `export` ... |
| create | POST이고 경로가 중괄호 없이 끝남 | `create`, `add`, `invite`, `assign` ... |
| update | PUT, PATCH | `update`, `set*`, `rename` ... |
| delete | DELETE | `delete`, `remove`, `kick`, `revoke` ... |
| action | 그 밖의 POST (`/lifecycle/activate`) | 그 밖 |

### 2.2 field — 스키마 필드 하나 (트리를 펼친 것)

```yaml
schema_id: okta.AppUser
path: "$.credentials.password"           # 배열은 [*]
type: object
format: null
enum: null
read_only: false
write_only: true
ref_schema: okta.PasswordCredential      # $ref 가 가리키는 것
discriminator: null                       # 있으면 값 → 하위 schema
in: [request, response]                   # 어느 쪽에 나오나
hole: null                                # 아래 표
description: "..."                        # 규칙은 안 읽는다
src: {...}
```

요청 스키마와 응답 스키마를 **둘 다** 펼친다. 쓰기 전용 비밀값과 설정 필드는 요청에만 있는 경우가 많다.

`hole`(구멍) 표시는 기계로 정한다.

| 값 | 조건 | 예 |
|---|---|---|
| `object_no_props` | object인데 `properties`, `oneOf`, `allOf` 없음 | GitHub PAT 승인 `permissions.repository` (GHEC 명세에 92개) |
| `json_string` | string인데 JSON을 담는다고 명세가 표시 (`contentMediaType`, `format: json`) 또는 구멍 사전에 등록 | Apps Script `appsscript.json` 내용 |
| `example_only` | 응답 예시에는 있는데 스키마에 없음 | Slack `apps.manifest.export`의 `manifest` |
| `open_map` | `additionalProperties`만 있음 | 사용자 정의 속성 맵 |

구멍마다 `fill: <외부 스키마 source_id>`를 붙이면, 그 스키마를 펼친 필드가 이 자리 아래로 들어온다. `fill`이 없는 구멍은 「추가로 필요한 자료」 목록이다.

### 2.3 event — 감사 로그와 웹훅/이벤트를 한 형식으로

```yaml
event_id: slack.audit.user_channel_join
provider: slack
catalog: audit                           # audit | webhook | event_api
name: user_channel_join                  # 벤더 action / event type 그대로
entity_types: [user, channel]            # 벤더가 적은 대상 종류 그대로
actor_path: "$.actor.user.id"
target_paths: ["$.entity.channel.id"]
payload_schema: slack.audit.entry        # 있으면
can_trigger: false                       # webhook, event_api 는 true
retention: null                          # 카탈로그 단위 값이면 manifest 에
src: {...}
```

### 2.4 grant_vocab — 권한 어휘 하나

```yaml
grant_id: google.scope.gmail.send
provider: gws
kind: oauth_scope                        # oauth_scope | app_permission | role | privilege
name: https://www.googleapis.com/auth/gmail.send
level: null                              # 벤더가 read/write/admin 을 주면
declared_resource: null                  # 벤더가 대상 종류를 적었으면 (GitHub "contents")
op_ids: [gmail.users.messages.send]      # 이 권한이 필요한 동작. operation.scopes 를 뒤집어 만든다
src: {...}
```

`op_ids`는 대부분 기계로 나온다. Google과 Okta는 명세가 동작마다 scope를 주고, Slack은 메서드 문서가 준다.

## 3. 후보를 결정론으로 뽑기

### 3.0 ID 공간

**ID 공간은 같은 종류의 대상을 가리키는 ID가 들어가는 자리들의 묶음이다. 후보 하나는 ID 공간 하나다.** 타입 수준 개념이라 개별 ID 값이 아니라 「어느 필드와 파라미터에 같은 종류의 ID가 들어가나」를 묶는다. 「후보 하나를 어디서 어디까지로 보나」를 LLM 없이 정하려고 둔 개념이다.

**왜 ID인가.** 이름과 경로로 정하는 방식은 이미 실패했다. Okta 정책 하위 타입마다 후보가 따로 생겼고(12개), 318건에 같은 provider 안의 이름 중복이 8건 있었고, Slack 채널 하나가 `conversations`, `channels`, `channel` 세 이름이며, Okta `AppUser.id`는 사용자 id라 이름으로 보면 배정이 사용자에 합쳐진다. ID는 벤더가 「이 값이 같으면 같은 대상」이라고 선언한 것이라 해석이 필요 없고, Object Schema의 `identifiers.primary`와 팔란티어의 primary key와 같은 기준이다.

**어떻게 묶나.** 같은 종류의 ID가 들어가는 자리끼리 같은 공간이다.

| 증거 | 예 |
|---|---|
| 경로 파라미터 이름 | `/users/{userId}`와 `/apps/{appId}/users/{userId}`의 `{userId}` |
| 경로 파라미터와 응답 필드 | `GET /users/{userId}`의 응답 `id` |
| 같은 스키마 | `repository.owner`가 `simple-user` 스키마 |
| ID 접두사 | Slack `U…`, `C…`, `T…` |
| 참조 필드 이름 줄기 | `user_id`, `channel_id` |

공간 이름은 파라미터 이름에서 꼬리(`Id`, `_id`, `Key`, `_slug`, `IdOrLabel` ...)를 뗀 것이다. 꼬리 목록은 사전이다.

**주인.** 그 공간을 마지막 자리에서 받는 가장 짧은 경로가 주인이다. user 공간의 주인은 `/users/{userId}`다. 주인이 정해지면 두 가지가 따라 나온다.

- 자기 ID인가: `/apps/{appId}/users/{userId}`의 응답 `id`는 user 공간인데 주인이 따로 있으므로 자기 것이 아니다
- 관계인가: 마지막 공간의 주인이 따로 있는 경로는 관계이고, 키는 지나온 공간의 조합(`[app, user]`)이다. `/repos/{o}/{r}/hooks/{hook_id}`는 hook 공간의 주인이라 관계가 아니라 저장소에 속한 대상이다

**범위.** 전역에서 유일하면 키가 `[id]`, 부모 안에서만 유일하면(GitHub 이슈 `number`) `[부모, number]`다. 부모 파라미터 뒤에서만 쓰이는 공간이 부모 범위다.

**자기 ID가 없을 때.** ID 공간은 「키를 만들 수 있는 방법」 전체를 뜻한다. 아래 넷은 모두 Object Schema가 허용하는 키다.

| 경우 | 키 | 예 | 규칙 |
|---|---|---|---|
| 다른 대상 둘의 관계 | 공간의 조합 | Okta 그룹 멤버십 `[group, user]`, Slack 앱 설치 `[app, team]` | E3 |
| 부모 안에 하나뿐 | 부모 키 + 종류 이름 | Branch Protection `[repo, branch, "protection"]`, Okta `/org` | E1 하나짜리 |
| 이름이나 값이 식별자 | 부모 키 + 이름, 또는 값의 해시 (키 구성만 정하고, 해시는 인스턴스마다 수집 때 계산) | Actions Secret `[repo, name]`, webhook URL 해시 | E1, E7 |
| 응답 안에 내장 | 부모 키 + 내장 ID | workflow 단계 `[workflow, step.id]` | E2 |

**키를 정말 만들 수 없을 때**(GitHub Actions의 `on:` 선언처럼 YAML 안 문장)는 Object가 될 수 없다(Object Schema 「식별자를 만들 수 없는 대상은 수집하지 않는다」). 후보 단계에서는 버리지 않고 `field_derived`로 기록하고 `key: none`을 표시한다. 판정 단계가 부모의 속성이나 관계로 접는다.

Slack 트리거는 이 경우가 아니다. `Ft…` ID가 있고 목록 API가 없을 뿐이라 E6이 `ref_only` 후보로 잡는다. 주소 없는 트리거를 Object로 세우지 않는 것은 판정 단계의 Interface 기준 때문이지 키가 없어서가 아니다.

**대기열로 보내는 경우.** 한 자리에 여러 공간이 옴(GitHub `{owner}`, GWS `{memberKey}`), 이름 줄기와 접두사가 다른 답을 냄(Slack `context_team_id`의 `E…` 값), 증거끼리 충돌. 자동으로 합치지 않는다.

**공간은 타입 수준 개념이다.** 후보 추출은 「이 필드에는 어느 공간의 ID가 들어가나」를 정할 뿐 개별 값을 맞추지 않는다. 값 단위 연결(어느 감사 로그 행이 어느 사용자인가)은 수집 이후 인스턴스 수준의 일이다.

**API 밖 세 자료와의 관계.** 세 자료는 대부분 새 공간을 만들지 않고, 자기 필드나 항목을 API가 세운 공간에 배정한다(3.2-b의 다리 B1~B4).

| 자료 | 공간에 배정하는 것 | 다리 | 공간을 새로 만드는 경우 |
|---|---|---|---|
| 감사 로그 | entity의 ID 필드, 행위자와 대상 필드. 대상이 둘인 action은 두 공간의 조합(관계)에 배정 | B3 접두사, B4 별칭. GitHub처럼 이름 문자열(`repo`)이면 B4이고 `name_key`로 표시 | 어느 공간에도 안 맞는 entity → `event_only` |
| 이벤트, 웹훅 | payload의 ID 필드. 이벤트를 일으키는 쪽 공간에 `emits_events` | B1 스키마 공유, B3 | 같음 |
| 권한 어휘 | 값이 없어 ID로는 못 잇는다. 권한 → 동작 → 그 동작이 속한 공간 | B2 동작 연결, 권한 이름의 자원 토큰은 B4 | 가리키는 동작이 없는 권한 → `vocab_only`. 키는 `(provider, 권한 이름)`으로 두고 판정 단계에서 정함 |

역할은 예외적으로 자기 ID를 가진 공간이다(Slack `Rl…`, Okta 역할 id). API에 목록이 없어도 배정 응답의 `role_id`로 E6이 공간을 만든다.

### 3.1 필드 분류 (③)

모든 `field`에 `class` 하나를 붙인다. 위에서부터 처음 맞는 것. 이름 목록은 사전 `field_lexicon`(버전 관리)에 있다.

| class | 조건 |
|---|---|
| `id` | 경로 파라미터와 같은 이름(`appId` ↔ `id`, `{team_slug}` ↔ `slug`), 또는 레코드 맨 위 `id`, `key`, `name`이고 그 레코드의 동작 경로가 이 값을 받음 |
| `ref` | `$ref`가 `id` 필드를 가진 스키마, 또는 이름이 `*_id`, `*Id`, `*_ids`, `*Ids`, `*_by`, `*By` |
| `secret` | `write_only`, 또는 이름이 비밀값 사전에 있음 (`client_secret`, `token`, `private_key` ...) |
| `url` | `format: uri/url`, 또는 이름이 `*_url`, `*_uri`, `redirect_uris`, `request_url` ... |
| `scope` | 문자열 배열이고 값이나 이름이 `grant_vocab`에 있음 (`scopes`, `permissions`) |
| `flag` | 불리언이고 이름이 역할 사전에 있음 (`is_admin`, `is_owner` ...) |
| `time` | `format: date-time`, 또는 이름이 시각 사전에 있음 |
| `link` | `_links`, `href`, `*_url`인데 같은 API의 경로 |
| `state` | 그 밖의 enum, 불리언 |
| `other` | 나머지 |

`link`와 `url`이 갈리는 기준은 「명세의 예시 값이나 경로 템플릿의 호스트가 그 SaaS의 API 호스트인가」다. 예시가 없으면 이름 사전으로 정하고, 둘 다 없으면 대기열이다. API 항해 링크(`hooks_url`)는 Endpoint가 아니다.

### 3.2 후보 생성 규칙 (④)

모든 규칙은 후보 하나와 근거(`rule`, 기록 id)를 낸다. 같은 후보가 여러 규칙에서 나오면 근거가 쌓인다.

| 규칙 | 입력 | 후보 | 이전 규칙 |
|---|---|---|---|
| E1 경로 | operation | REST: 중괄호 앞 단어까지의 경로. 중괄호 없이 끝나는 경로는 GET이 있으면 하나짜리(singleton). RPC: 메서드 이름에서 마지막 동사 토큰을 뺀 이름공간(`admin.users.setAdmin` → `admin.users`). 다른 명사가 붙은 읽기(`conversations.members`)는 별도. GraphQL: `Node`를 구현한 타입. AIP: `flatPath` 기준 | R1 + RPC, GraphQL, AIP |
| E2 내장 객체 | field | `id` class 자식을 가진 object, 또는 그런 object의 배열. 부모 후보 안의 내장 후보 | R2를 중첩까지 |
| E3 관계 | operation, field | (a) `/A/{a}/B/{b}` 경로이고 B의 ID 공간을 다른 후보가 가지면 A×B 관계 후보. (b) create/update/delete 동작이 서로 다른 ID 공간의 인자를 둘 이상 받고 반대 동사가 있으면 그 조합의 관계 후보. (c) `flag` class 필드면 (레코드, 상위 Tenant) 관계 후보. (d) list 동작이 A 공간의 인자를 받고 B 공간의 ID만 담은 배열을 돌려주면 A×B 관계 후보 (`conversations.members`) | 새 규칙 |
| E4 이벤트 | event | `entity_types`의 각 값. 이미 있는 후보면 근거만 더함 | 새 규칙 |
| E5 권한 어휘 | grant_vocab | `declared_resource`의 각 값, 그리고 `kind: role`이면 역할 자체 | 새 규칙 |
| E6 참조 대상 | field (`ref`) | 대상 타입. 경로 파라미터 이름 → `$ref` 스키마 → ID 접두사 사전(Slack `U`/`C`/`T`/`E`/`W`) → 이름 줄기(`channel_id` → channel) 순서. 대상 공간을 가진 후보가 없으면 `ref_only` 후보를 만든다(Slack `role_id`). 못 정하면 대기열 | R4 일반화 |
| E7 필드 분리 | field (`url`, `secret`, `scope`) | 부모 후보의 하위 후보. `derived_from_field: true`. 실제로 떼어 낼지는 판정 단계가 정함 | 새 규칙 |

### 3.2-b API 밖 세 자료의 처리

**API가 ID 공간을 먼저 세우고, 나머지 셋은 그 공간에 「다리」로 붙는다.** 다리에 못 붙는 것만 새 후보(`event_only`, `vocab_only`)가 되고 대기열에 들어간다. API가 없는 대상은 여기서 나온다.

다리는 넷이고 위에서부터 쓴다. 이름 대조는 마지막이다.

| 다리 | 무엇으로 잇나 | 예 |
|---|---|---|
| B1 스키마 공유 | 이벤트 payload가 API와 같은 `$ref` 스키마를 씀 | GitHub 웹훅(OpenAPI 3.1 `webhooks`)은 `repository`, `simple-user`를 API와 같이 씀 |
| B2 동작 연결 | 권한 어휘의 `op_ids`가 이미 후보에 붙은 동작을 가리킴 | Google `gmail.send` → `users.messages.send` → Message 후보 |
| B3 ID 모양 | ID 접두사 사전이나 명세 예시 값의 접두사가 API 공간과 같음 (실측 값이 아니라 타입 수준 자료) | Slack 감사 `entity.user.id = U…`, 이벤트 `channel: C…` |
| B4 이름 사전 | 별칭 사전(사람이 관리)에 등록된 이름 | Slack 감사 entity `workspace` ↔ API `team` |

**감사 로그 카탈로그**

1. entity 종류마다: 카탈로그가 준 entity 스키마(Slack `audit/v1/schemas`)의 필드를 ③으로 분류하고, `id` 필드를 다리 B3, B4로 API 공간에 잇는다. 못 이으면 `event_only` 후보
2. action마다: 이름을 토큰으로 나눠 동사 쌍 사전에 대조한다(`added`/`removed`, `join`/`leave`, `assigned`/`revoked`, `created`/`deleted`). 행위자를 뺀 대상 entity가 둘이고 동사 쌍이 맞으면 **관계 근거**(E4b)를 낸다. 예: Slack `workflow_collaborator_added`/`removed` → workflow×user, Okta `group.user_membership.add`/`remove` → group×user
3. 후보마다 `features.audited_actions[]`를 채운다. 「벤더가 보안상 기록하는 변경」 목록이다
4. `details` 구조는 action마다 달라 대개 `open_map` 구멍이다. 구조를 준 action만 ③으로 분류한다

**이벤트, 웹훅 카탈로그**

1. 이벤트마다 payload 스키마를 ③으로 분류하고, `id`, `ref` 필드를 다리 B1, B3, B4로 잇는다
2. 이벤트를 일으키는 대상(출처)에 `features.emits_events[]`를 채운다. `triggered_by`의 Resource, Integration 끝점을 판정할 근거다
3. 이벤트 이름에 동사 쌍이 있으면 감사 로그와 같은 방식으로 관계 근거를 낸다. 예: Slack `member_joined_channel`/`member_left_channel` → channel×user, GitHub `member` 이벤트의 `added`/`removed` → repository×user
4. Okta Event Hook은 payload가 System Log 이벤트라 감사 로그 처리와 같다

**권한 어휘 카탈로그**

1. 어휘마다 `op_ids`를 다리 B2로 잇는다. 이름 대조 없이 「이 권한이 어느 후보를 읽고 쓰는가」가 나온다. 후보마다 `features.read_by[]`, `write_by[]`를 채운다
2. **`op_ids`가 비어 있는 어휘**는 API 동작이 아닌 능력이다. 예: Slack `incoming-webhook`, `commands`. 이것이 `vocab_only` 후보가 되어 API 없는 대상(incoming webhook)을 잡는다
3. 권한 이름에 구조가 있으면 나눠서 자원 토큰을 B4로 잇는다. 예: Okta `okta.<자원>.<동작>`(`okta.users.manage`), GitHub fine-grained `contents`, `members`
4. 역할은 역할 자체가 후보(나중에 Policy 판정 대상)이고, 역할 → 권한 목록은 그 후보의 `features.grants[]`가 된다

| 자료 | 이 자료만 주는 것 |
|---|---|
| API 명세 | ID 공간, 키, 구조, 읽기와 쓰기 동작 |
| 감사 로그 | 보안상 기록되는 변경, API에 없는 대상, 목록 API 없는 관계 |
| 이벤트, 웹훅 | 무엇이 자동화를 시작시킬 수 있는가 |
| 권한 어휘 | 무엇을 부여할 수 있고 그 권한이 어느 대상에 닿는가, API 동작 없는 능력 |

### 3.3 합치기 (⑤)

후보 키는 `(provider, service, id_space)`다. 같은 ID 공간인지는 이 순서로 본다.

1. 같은 스키마(`schema_id`, `$ref`)의 `id` 필드
2. discriminator로 묶인 하위 스키마 → 기반 스키마 하나 (R3)
3. 같은 경로 파라미터 이름을 정규화한 것 (`{userId}`, `{user_id}`)
4. 같은 ID 접두사

**이름이 비슷하다는 이유로는 합치지 않는다.** 위 넷이 서로 다른 답을 내면 합치지 않고 대기열에 넣는다. 후보 이름은 Object_Schema의 우선순위(응답 필드 > 감사 entity > 메서드 경로)로 정하고, 밀린 이름은 `aliases`에 남긴다.

### 3.4 폐포 검사 (⑥)

| 검사 | 대응해야 하는 것 | 안 맞으면 |
|---|---|---|
| C1 참조 | 모든 `ref` 필드와 경로 파라미터의 대상 타입 | 대기열 `unresolved_ref` |
| C2 감사 | 감사 카탈로그의 모든 `entity_types` | `audit_only` |
| C3 이벤트 | 이벤트 카탈로그의 모든 대상 타입 | `event_only` |
| C4 권한 | 모든 `grant_vocab`의 `op_ids`와 `declared_resource` | `vocab_only` |
| C5 쓰기 | 모든 create/update/delete 동작의 대상(인자 ID 조합) | `write_target` |
| C6 구멍 | 모든 `hole` | `hole_unfilled` (= 추가 자료 목록) |

대기열은 사람이 「후보로 추가」, 「사전에 단어 추가」, 「범위 밖」 중 하나로 닫는다. 앞의 둘은 사전이나 고정 자료를 고치는 것이라 다시 돌리면 같은 결과가 나온다. **대기열이 비거나 모든 항목이 닫혔을 때를 「빠짐없음」으로 정의한다.**

### 3.5 출력

```yaml
candidate_id: cand_8f3a...               # (provider, service, id_space) 의 해시. 다시 돌려도 같다
provider: okta
name: AppUser
aliases: [users]
kind: association                        # entity | singleton | embedded | association | field_derived | ref_only | event_only | vocab_only
key: [app_id, user_id]                   # E6 과 경로 파라미터에서
parent: cand_app...                       # 경로나 내장 관계
evidence:
  - {rule: E1, record: okta.listApplicationUsers}
  - {rule: E3a, record: okta.getApplicationUser}
  - {rule: E4, record: okta.event.application.user_membership.add}
features:                                # 판정 단계(Interface 구조 신호)가 읽는 값
  own_id: false                           # 레코드 id 가 자기 것인가 (AppUser.id 는 사용자 id)
  read_ops: [list, get]
  write_ops: [create, update, delete]
  revoke_op: true
  refs_out: [app, user]
  refs_in: []
  field_classes: {secret: 1, url: 0, scope: 1, flag: 0, state: 3}
  audited_actions: [application.user_membership.add, application.user_membership.remove]
  emits_events: []
  read_by: [okta.apps.read]
  write_by: [okta.apps.manage]
  grants: []                              # 역할 후보일 때만
queue: []
```

`features`가 판정 단계의 유일한 입력이다. 판정 단계는 원본 자료를 다시 읽지 않는다.

## 4. 예시 셋

**Okta AppUser.** E1이 `/api/v1/apps/{appId}/users`를 후보로 낸다. E3a가 `/apps/{appId}/users/{userId}`에서 app×user 관계 후보를 내고, ⑤가 둘을 같은 ID 공간으로 합친다. `id` 필드는 경로 파라미터 `userId`와 같으므로 사용자 ID 공간이다. 그래서 `own_id: false`이고 키는 `[app_id, user_id]`다(Object_Schema의 AppUser 설명과 같다).

**Slack 워크스페이스 관리자.** E1은 `admin.users`(이름공간)를 낸다. E3b는 `admin.users.setAdmin(team_id, user_id)`가 서로 다른 두 후보의 ID를 받고 반대 동사 `setRegular`가 있으므로 team×user 관계 후보를 낸다. E3c는 `admin.users.list` 응답의 `is_admin` flag에서 같은 관계 후보를 내고, ⑤가 합친다.

**Slack manifest의 Endpoint.** `apps.manifest.export` 응답 스키마에 `manifest`가 없으므로 ②가 `example_only` 구멍을 표시한다. manifest 레퍼런스 스키마로 `fill`하면 `settings.event_subscriptions.request_url` 등이 `url` class가 되고, E7이 하위 후보를 낸다. `fill`하기 전에는 C6이 「추가 자료 필요」로 남긴다.
