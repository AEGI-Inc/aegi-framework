# ID 공간 설계 (API 스키마가 있다는 가정)

2026-10-14. 「정보 지도 설계.md」의 ①~③(자리, 결정자, 항목)을 스키마만으로 정하는 절차를 다시 쓴다. 지금 구현(`extract.py` `schema_spaces`, `info_map.py`)에서 드러난 논리 오류를 고친 판이다.

## 요약

- ID 공간은 「한 종류의 대상을 가리키는 식별자 값의 집합」이다. 스키마는 값의 모양만 알려 주고 「두 자리의 값이 같은 집합에서 나온다」는 사실은 직접 말하지 않는다. 그래서 공간은 이름으로 정하지 않고, 같은 값 집합이라는 **근거가 있는 자리끼리 묶은 동치류**로 정한다.
- 근거는 네 가지이고 세기가 다르다. 왕복(같은 값을 넣고 꺼냄) > 명시 참조($ref, Refers To, 판별자) > 사전(사람이 정함) > 이름 비슷함. 앞의 둘만 자동으로 묶고, 뒤의 둘은 등급을 달아 후보로 둔다.
- 파라미터 이름은 근거가 아니다. 같은 `{id}`라도 경로 위치가 다르면 다른 자리다. 근거의 단위는 「정규화한 경로 틀 안의 위치」다.
- 키는 범위(scope) 안에서만 유일하다(`number`는 저장소 안, `ts`는 채널 안). 공간은 「범위 공간 + 지역 키」로 쓴다.
- 정보는 「가장 가까운, 키가 있는 레코드」에 붙는다. 키가 없는 객체는 공간이 아니라 그 레코드의 속성 묶음이다.
- 스키마만으로 닫히지 않는 질문(REST `id`와 감사 로그 `repo_id`가 같은 값인가)은 가설로 남기고 실측으로 확인한다.
- 스키마가 불완전하면(2부, 13절) 이름 문자열 대신 구조 지문, 스스로 형식을 밝히는 ID 값, 예시 값 공출현, 타입이 있는 다른 명세, 실측을 근거로 쓴다. 이름 변형과 다른 명명 체계끼리의 이름 맞추기는 결정에 쓰지 않는다.

## 1. 용어

| 용어 | 정의 |
| --- | --- |
| 자리 (slot) | (동작, 쪽, 경로). 쪽은 request, response, payload, audit |
| 경로 틀 | 경로에서 파라미터 이름을 지운 것. `/repos/{}/{}/issues/{}` |
| 경로 위치 | (경로 틀, n번째 파라미터). 파라미터 자리의 정체다 |
| 레코드 | 응답 안에서 키 후보를 가진 객체 자리 |
| 키 | 레코드를 범위 안에서 하나로 가리키는 필드(또는 필드 묶음) |
| 범위 | 키가 유일한 영역. 테넌트, 또는 다른 공간의 한 대상(저장소, 채널) |
| ID 공간 | 같은 값 집합에서 값을 받는 키 자리와 참조 자리의 동치류. 이름은 대표 이름일 뿐이다 |
| 결정자 | 한 자리의 값이 어느 대상의 것인지 정하는 것. 공간 키, 범위 안 키, 키 조합, 사건, 정할 수 없음 |
| 항목 | 같은 결정자, 같은 상대 경로, 맞는 타입의 자리 묶음 |

## 2. 공리 (설계가 기대는 가정)

1. **A1 스키마는 구조를 말한다.** 필드 이름, 타입, 중첩, `$ref`, `oneOf`, `discriminator`, 필수 여부는 믿는다.
2. **A2 스키마는 값 집합의 같음을 말하지 않는다.** 두 필드의 이름과 타입이 같아도 같은 대상을 가리킨다는 보장은 없다(`comment_id`는 이슈 댓글일 수도, 커밋 댓글일 수도 있다).
3. **A3 단건 조회 계약.** `GET …/{p}`가 성공하면 돌려준 레코드는 p가 가리키는 대상이다. 그래서 p의 값과 그 레코드 키의 값은 같은 공간이다. 문서가 깨는 경우(래퍼, 다른 대상 반환)는 예외 사전으로 다룬다.
4. **A4 `$ref`의 같음.** 두 자리가 같은 스키마를 참조하면 같은 구조다. 같은 공간이라는 뜻은 아니다(`simple-user`가 작성자에도, 담당자에도 쓰인다). 같은 공간인 것은 그 스키마의 **키 자리**다.
5. **A5 키 유일성은 범위 안에서만 성립한다.** 범위는 경로 부모로 정한다(A6).
6. **A6 경로 부모가 범위다.** `/repos/{o}/{r}/issues/{n}`의 n은 (owner, repo)가 정하는 저장소 안에서 유일하다. 단, 부모를 빼고도 같은 키로 단건 조회가 되면(`/issues/{id}` 같은 최상위 경로) 범위는 테넌트다.

## 3. 파이프라인

```
① 파싱          명세 -> 동작, 자리, 스키마 그래프 (형식 변환만)
② 키 후보       스키마마다 키 후보를 정한다
③ 근거 간선     자리 사이에 「같은 값 집합」 근거를 긋는다 (등급 포함)
④ 공간          강한 근거로만 동치류를 만든다. 충돌은 검사한다
⑤ 범위와 키 꼴  공간마다 범위와 키 꼴(단일, 지역, 조합, 다형)을 정한다
⑥ 정보 매핑     모든 응답 자리를 결정자에 붙이고 항목으로 묶는다
⑦ 검증          불변식 검사, 대기열
```

각 단계는 앞 단계 출력만 읽는다. 단계 안에서는 정렬된 순서로 처리해 결과가 바이트 단위로 같게 한다.

## 4. ① 파싱

명세 형식(OpenAPI, Discovery, sObject 정의, GraphQL SDL)마다 변환기 하나를 둔다. 출력은 같은 꼴이다.

- 동작: 동작 ID, HTTP 메서드, 경로 틀, 파라미터(이름, 위치 path, query, body, 타입), scope
- 스키마 그래프: 스키마 이름 → 속성(이름, 타입, `$ref`, 배열 여부, `oneOf` 대안, 판별자 필드와 값 표)
- 자리: 동작마다 요청과 응답을 스키마 그래프로 펼친 경로. 각 객체 자리에 그 자리를 채운 스키마 이름을 단다(펼치기 전 `$ref` 이름)

규칙:

- `$ref`를 펼칠 때 스키마 이름을 잃지 않는다. 이름 없는 인라인 객체는 「(동작, 경로)」를 이름으로 쓴다.
- `oneOf`, `anyOf`는 대안마다 스키마 이름을 남긴다. 자리 하나에 스키마가 여럿 달린다.
- 순환 참조는 한 번 펼친 뒤 멈추고 「순환」 표시를 단다.
- 사용자 정의 메서드(`{id}:undelete`)는 경로 단어로 나눈다.

## 5. ② 키 후보

스키마 S의 키 후보 K(S)는 다음 순서로 정한다. 앞에서 정해지면 뒤는 보지 않는다.

1. **명시:** 명세가 키를 말한다. sObject `Id`, GraphQL `Node.id`, OpenAPI 확장 표시, Discovery 자원 이름(`name`이 `groups/{id}` 꼴)
2. **왕복:** S를 단건 조회로 돌려주는 동작 `GET …/{p}`가 있고, S의 필드 f 하나만 p와 타입과 형식이 맞으면 K(S) = {f}. 여러 필드가 맞으면 사전 `record_key_fields` 순서로 고른다
3. **관례:** 사전 `record_key_fields`(id, number, key ...)와 「스키마 이름 + Id」(roleId)

키 후보가 없는 스키마는 레코드가 아니다. 다른 레코드의 속성 묶음(값 객체)이다.

주의:

- `accountId`처럼 다른 대상을 가리키는 필드를 관례 키에 넣으면 참조만 하는 레코드(versionapprover)가 레코드가 된다. 관례 키는 「이 스키마 자신의 이름」과 이어진 것만 쓴다.
- `name`은 표시 이름일 때가 많다. 형식(자원 이름 꼴)이나 왕복 근거가 있을 때만 키다.

## 6. ③ 근거 간선

자리 x, y 사이의 간선 E(x, y, 등급)는 「x와 y의 값이 같은 공간에서 나온다」는 근거다. 키 자리와 참조 자리, 경로 위치가 꼭짓점이다.

| 등급 | 간선 | 조건 |
| --- | --- | --- |
| 왕복 (structural) | 경로 위치 p ↔ 레코드 키 K(S) | A3. 단건 조회 `GET …/{p}`가 S를 돌려준다 |
| 왕복 | 경로 위치 p ↔ 경로 위치 q | 같은 경로 틀에서 같은 위치(GET과 PATCH, DELETE가 같은 `…/{p}`). 경로 틀이 같으면 메서드가 달라도 같은 자리다 |
| 왕복 | 목록의 원소 키 ↔ 같은 컬렉션 단건 경로 위치 | `GET /c`의 원소 스키마 키와 `GET /c/{p}`의 p |
| 명시 (stated) | 참조 필드 ↔ 대상 스키마 키 | `$ref`가 키 있는 스키마를 가리키는 필드의 키, sObject Refers To, OpenAPI links, 판별자 표 |
| 명시 | 같은 스키마의 키 자리끼리 | A4. 같은 스키마 S가 여러 동작에 나오면 그 키 자리는 모두 같은 공간 |
| 사전 (curated) | 사전이 정한 같음 | 표현 스키마 표(`full-repository` = `repository`), 필드 이름 표(`repo_id` → repo), 다른 출처(감사 로그)의 필드 |
| 이름 (heuristic) | 이름이 비슷함 | 접사를 뗀 이름이 같음, 이름 꼬리가 같음. 간선을 긋지 않고 후보로만 남긴다 |

넣지 않는 것:

- 파라미터 **이름**이 같다는 이유로 긋는 간선. 근거의 단위는 경로 위치다. 같은 `{comment_id}`라도 `/issues/comments/{}`와 `/gists/{}/comments/{}`는 다른 위치다.
- 「객체가 다른 객체 안에 있다」는 간선. 그것은 같은 공간이 아니라 참조나 구성이다.

## 7. ④ 공간 (동치류)

1. 왕복과 명시 간선으로만 합집합 찾기(union-find)를 돌린다. 각 동치류가 공간 후보다.
2. 사전 간선은 그다음에 더한다. 사전이 합치는 두 동치류가 아래 충돌 검사를 통과할 때만 합친다.
3. 이름 간선은 합치지 않는다. 「합칠 만함」 대기열로 보낸다.

충돌 검사. 아래가 하나라도 성립하면 그 합치기는 틀렸다.

- **C1 같은 레코드의 다른 키:** 한 레코드 스키마의 서로 다른 필드 두 개가 같은 동치류에 들어간다(id와 참조 필드가 한 공간). 단, 사전이 「대체 키」(id와 login)로 정한 쌍은 예외로 하고 대체 키 표에 적는다.
- **C2 판별자 충돌:** 한 동치류의 레코드들이 같은 판별자 필드에 서로 다른 고정값을 가진다(`type: CodeScanningAlert`와 `type: DependabotAlert`). 다형 상위 공간을 만들고, 그 아래 하위 공간으로 둔다.
- **C3 범위 충돌:** 범위가 다른 두 키(저장소 안 `number`와 테넌트 전역 `id`)가 한 동치류에 들어간다. 키 꼴이 다르면 같은 대상이라도 공간을 나누고 「대체 키」로 잇는다.

대표 이름. 이름은 정체가 아니다. 동치류 안 이름 후보를 정해진 순서로 골라 대표 이름으로 쓴다.

1. 사전이 정한 이름
2. 단건 경로가 가장 많은 경로 위치의 앞 단어
3. 키 스키마 이름(접사를 뗀 것)

같은 순서, 같은 입력이면 같은 이름이 나온다.

## 8. ⑤ 범위와 키 꼴

공간마다 키 꼴을 정한다.

| 키 꼴 | 조건 | 결정자 표기 |
| --- | --- | --- |
| 전역 | 최상위 단건 경로(`/x/{p}`)로 조회되거나, 명시 키 | `space:x` |
| 범위 안 | 단건 경로에 부모 공간 위치가 있고 최상위 단건 경로가 없다 | `local:부모/x` |
| 조합 | 자기 키가 없는 레코드가 참조 둘 이상으로만 식별된다(역할 배정) | `combo:a+b+c` |
| 다형 | 판별자로 나뉘는 하위 공간의 상위 | `poly:x` (하위 공간을 담는다) |

규칙:

- 테넌트(조직, 워크스페이스)는 범위다. 결정자가 아니다. 단, 레코드 안의 테넌트 참조는 조합의 한 자리일 수 있다(역할 대상이 워크스페이스).
- 같은 대상에 전역 키와 범위 안 키가 함께 있으면(GitHub 이슈의 `id`와 `number`) 전역 공간 하나에 대체 키로 둔다. 범위 안 키는 「(범위, 키) → 전역 키」 대응 표가 된다.

## 9. ⑥ 정보 매핑

응답, payload, 감사 필드의 모든 자리 x에 결정자 D(x)와 상대 경로 R(x)를 준다.

1. x에서 위로 올라가며 처음 만나는 레코드 자리 r을 찾는다(x 자신이 레코드 키면 r은 그 레코드).
2. r이 있으면 D(x) = r의 공간과 키 꼴, R(x) = r에서 x까지의 경로(배열 표시 `[*]`는 지운다).
3. r이 없으면 동작 맥락으로 정한다.
   - 단건 경로(`…/{p}`)이면 p의 공간
   - 경로가 단어로 끝나면 마지막 경로 위치의 공간(`/issues/{}/lock` → issue)
   - 목록과 검색 동작은 정할 수 없음(`op:` 결정자). 질의 인자는 필터이지 결정자가 아니다
   - 이벤트 payload는 사건, 감사 필드는 감사 사건
4. r이 응답 최상위가 아니라 다른 레코드 안에 박혀 있으면 「사본」 출처다. 그 대상의 정보이지만 바깥 동작이 함께 실어 준 것이다.

항목. (D, R)이 같은 자리를 한 항목으로 묶는다. 타입이 다르면 묶지 않고 대기열에 둔다.

참조. 레코드 r의 필드 f가 다른 공간 T의 키를 가리키면(③의 명시 간선), 항목 (D(r), f)는 T로 가는 참조 간선이 된다. 배열이면 다대다다.

요청은 자리가 아니다. 요청 본문 경로가 대상 공간의 항목 경로와 같으면 그 항목의 「쓰는 동작」이 된다(S2). 질의 인자는 그 동작 응답 항목의 「거르는 조회」가 된다.

## 10. ⑦ 불변식

출력이 아래를 모두 만족해야 한다. 어기면 대기열로 보낸다.

| 번호 | 불변식 |
| --- | --- |
| V1 | 모든 공간에 키 자리가 하나 이상 있다 |
| V2 | 한 자리는 결정자 하나에만 속한다 |
| V3 | 한 공간 안에서 (상대 경로)는 항목 하나다. 타입이 다르면 대기열 |
| V4 | 근거 없이 합친 동치류가 없다. 모든 합치기에 간선과 등급이 남아 있다 |
| V5 | 충돌 검사 C1~C3을 통과한다 |
| V6 | 같은 입력과 같은 사전이면 같은 출력(sha256)이다 |
| V7 | 경로 위치마다 공간이 하나다. 정하지 못한 위치는 「경로 단독」으로 표시한다 |

## 11. 스키마만으로 닫히지 않는 것

스키마가 다 있어도 아래는 문서로 증명할 수 없다. 가설로 두고 등급을 단다.

| 질문 | 예 | 닫는 길 |
| --- | --- | --- |
| 다른 출처의 필드가 같은 값 집합인가 | 감사 로그 `repo_id`와 REST `repo.id`, GraphQL `node_id`와 REST `id` | 실측 값 겹침 검사. 같은 대상의 두 값을 함께 뽑아 맞춰 본다 |
| 키가 정말 유일한가 | Jira 이슈 key는 프로젝트 이동 뒤 바뀐다 | 수명(불변성) 표시. 바뀌는 키는 대체 키로만 둔다 |
| 참조가 어느 공간인가 (다형) | Salesforce `WhoId`(Contact 또는 Lead) | 값 접두사(`003`, `00Q`), 판별자 필드. 접두사는 실측 등급 |
| 범위가 무엇인가 | 같은 번호 체계를 쓰는 이슈와 PR | 문서 근거가 없으면 경로 부모로 정하고 실측으로 확인 |

## 12. 지금 구현과 다른 점

| 지금 구현 | 이 설계 | 바꿀 것 |
| --- | --- | --- |
| 경로 파라미터 이름으로 공간을 만든 뒤 이름 표로 합친다(`build_rest_spaces`, `param_space`) | 경로 위치가 꼭짓점이다. 이름은 대표 이름 고르기에만 쓴다 | `{comment_id}` 같은 같은 이름 다른 위치가 처음부터 나뉜다. 나중에 계열로 나누는 단계(`schema_spaces` 3번)가 필요 없어진다 |
| 스키마 계열을 접사 떼기로 정하고 「바탕 이름으로 끝나면 표현」으로 합친다 | 같은 공간인 근거는 왕복과 명시 간선뿐이다. 접사와 꼬리는 이름 간선(후보)이다 | `team-repository`는 키 `id`가 `/repos/{}/{}`의 왕복 간선과 이어질 때 합친다. 이름이 비슷해서 합치지 않는다 |
| `id`를 키로 가정하고 `number`, `name`은 사전으로 더한다 | 키는 명시, 왕복, 관례 순으로 스키마마다 정한다 | 왕복으로 `number`(GitHub), `alertId`(Google)가 자동으로 키가 된다 |
| 범위 안 키는 `ts`처럼 사전에 적은 것만 | 경로 부모가 있고 최상위 단건 경로가 없으면 범위 안 키 | GitHub 이슈 `number`는 저장소 안 키, `id`는 전역 키, 둘은 대체 키 |
| 다형은 이름 `@resolve`로만 | `oneOf`와 판별자로 다형 상위 공간과 하위 공간 | GitHub `alert`가 상위, 코드 스캔, 비밀값, Dependabot이 하위 |
| 합치기 근거가 기록되지 않는다 | 모든 합치기에 간선과 등급을 남긴다(V4) | `space_rebuild.json`에 간선 목록을 쓴다 |

## 13. 스키마가 불완전할 때 (2부)

1~12절은 스키마가 완전하다고 가정했다. 실제 자료는 그렇지 않다. 2부는 빈틈마다 무엇이 깨지는지, 이름 문자열을 비교하지 않고 무엇으로 메우는지를 정한다.

### 13.1 빈틈의 유형

일곱 SaaS에서 실제로 본 빈틈이다.

| 번호 | 빈틈 | 실제 예 | 깨지는 단계 |
| --- | --- | --- | --- |
| G1 | 응답 스키마가 없고 예시만 있다 | Slack 메서드 다수(예시에서 구조를 만든 `hole_example_only` 539건) | ② 키 후보(타입, 형식 없음), ③ 명시 간선(`$ref` 없음) |
| G2 | 스키마가 이름 없는 인라인이다 | GitHub 웹훅 payload 의 `repository`, `sender`, 익명 응답 객체 | ③ A4(같은 스키마) 간선을 못 긋는다 |
| G3 | 참조 필드가 그냥 문자열이다 | `owner_id: string`, Salesforce 이벤트의 `UserId: reference`(대상 없음), Okta `targetId` | ③ 명시 참조 간선이 없다 |
| G4 | 다형인데 `oneOf`, 판별자가 없다 | Slack `entity_id`(T, C, E), Okta System Log `target[].type`, Salesforce `WhoId` | ④ C2 충돌 검사를 못 한다 |
| G5 | 객체에 속성이 없다(열린 맵) | Jira `hole_open_map` 310, Confluence 765 | ⑥ 그 아래 정보가 자리로 안 나온다 |
| G6 | 감사, 이벤트 목록이 이름과 필드 이름뿐이다 | GitHub 감사 필드 목록, Google Reports 파라미터(타입만), Atlassian 표시 이름(필드 없음) | ③ 감사 필드와 API 항목 사이 간선이 없다 |
| G7 | 단건 조회가 없다 | GitHub `secret`, `variable`(목록만), Confluence 사용자(질의 인자로만 조회) | ③ 왕복 간선이 없다 |
| G8 | 출처끼리 어긋난다 | Slack 정리본은 Deprecated, 엑셀은 아님. GitHub 감사 목록은 2026-09-03판 | 같은 사실이 둘로 나온다 |

### 13.2 문자열 비교를 어디까지 허용하나

이름 비교 중 오류가 큰 것은 **서로 다른 명명 체계를 이름으로 맞추는 것**과 **이름을 변형해 맞추는 것**이다. 이 둘은 결정에 쓰지 않는다.

| 허용 (정확한 식별자 같음) | 결정에 쓰지 않음 (후보 생성에만) |
| --- | --- |
| 같은 명세 안의 `$ref` 이름이 같다 | 단수화, 접사 떼기(`full-`, `Bean`), 낙타 표기 나누기 |
| 같은 경로 틀, 같은 위치 | 포함, 꼬리 일치(`teamrepository`는 `repository`로 끝난다) |
| 같은 스키마 안 같은 필드 경로 | 토큰으로 쪼개 맞추기(감사 action `runner_group_removed` → runnergroup) |
| 명세가 정한 판별자 값 ↔ 스키마(판별자 표) | 다른 명명 체계끼리 이름 맞추기(감사 category `repo` ↔ REST 공간 `repo`, 감사 필드 `visibility` ↔ API 항목 `visibility`) |
| 사람이 출처를 달아 적은 사전 한 줄 | 이름이 비슷하다는 이유만의 합치기 |

사전은 문자열 표지만, 한 줄마다 근거(문서 쪽, 실측)를 적고 사람이 확인한 것이므로 결정에 쓴다. 자동 이름 변형으로 사전을 만들지 않는다.

### 13.3 문자열 대신 쓰는 근거

**V1 구조 지문.** 객체 자리의 「속성 이름 집합과 각 속성의 타입, 중첩 모양」. 이름 없는 인라인 객체(G2)를 이름 있는 스키마에 대응시킨다.

- 같은 명세 안에서 지문이 정확히 같으면 같은 스키마다(구조 근거).
- 한쪽이 다른 쪽의 부분집합이고, 키 필드를 함께 가지며, 겹친 속성의 타입이 모두 같으면 「같은 스키마의 다른 모양」 후보다. 키 값 근거(V2, V3)가 하나 더 있을 때 합친다.
- 속성 이름 집합 비교는 같은 명명 체계 안의 정확한 같음이다. 이름을 변형하지 않는다.

**V2 스스로 형식을 밝히는 ID 값.** 값 자체에 형식이 들어 있으면 공간을 값으로 정한다.

| 출처 | 형식 | 근거 등급 |
| --- | --- | --- |
| GitHub `node_id` | base64 안에 GraphQL 타입이 있다. 예시 `MDQ6VXNlcjE=` → `04:User1`, `MDEwOlJlcG9zaXRvcnkxMjk2MjY5` → `010:Repository1296269` | 명시(값이 타입을 말한다) |
| Slack ID | OpenAPI `defs_*` 패턴(`^[UW][A-Z0-9]{2,}$`) | 명시 |
| Google Cloud Identity | 자원 이름 `groups/{id}/memberships/{id}` | 명시 |
| Salesforce Id | 앞 세 자리 접두사(`005` = User). 목록은 describe(`keyPrefix`)로만 나온다 | 실측 |
| Okta ID | 접두사(`00u` = user)는 명세에 없다 | 실측으로만 쓴다 |

GitHub 예시 객체에 `node_id`가 있으면, 그 객체가 어느 GraphQL 타입인지 이름 비교 없이 정해진다. 실제 예시에서 `owner`, `user`, `creator`, `assignees[*]` 자리의 `node_id`가 모두 `User` 타입이었다(293곳).

**V3 예시 값 공출현.** 문서 예시는 같은 대상에 같은 값을 되풀이해 쓴다. 키 자리와 다른 필드에 **같은 희귀 값**이 나오면, 그 필드는 그 공간을 가리킨다(G1, G3).

- GitHub 예시에서 저장소 id `1296269`가 `repository`, `repo`, `template_repository`, `repositories[*]` 자리에 74번 나온다.
- Slack 예시에서 `U123ABC456`이 `id`, `user`, `user_id`, `users[*]`, `reply_users[*]`, `requester_ids[*]`에 나온다.
- 희귀성 조건: 그 값이 한 공간의 키 자리에서만 나와야 한다. `id: 1`은 466곳, 여러 타입에 쓰여 근거가 아니다. 값과 타입을 함께 보는 V2와 묶으면 모호함이 줄어든다(`(node_id 타입, id)` 쌍).
- 문서 예시는 손으로 쓴 것이라 틀릴 수 있다. 등급은 「예시」로 따로 둔다.

**V4 예시 왕복.** 같은 동작의 예시 요청 경로 값과 예시 응답 키 값이 같으면 왕복 근거다(G7을 일부 메운다). Google Reports 부록의 「Sample request」, Slack 문서의 요청 예시가 해당한다.

**V5 반대 근거(모순).** 값의 범위가 맞지 않으면 합치지 않는다. 이것은 결정을 막기만 하므로 오류가 적다.

- 타입: 정수 대 문자열
- 형식: uuid 대 정수, `^U` 패턴 대 `^C` 패턴
- 열거값 집합이 겹치지 않음
- 범위: 저장소 안 `number`와 전역 `id`(C3)

**V6 타입이 있는 다른 명세.** 같은 SaaS의 다른 기계용 명세가 빈틈을 메운다.

| 자료 | 메우는 빈틈 | 잇는 방법 (문자열 아님) |
| --- | --- | --- |
| GitHub GraphQL SDL (받아 둠) | G3, G4. 필드 타입이 객체 타입이라 참조가 명시다. `Node` 구현 타입이 공간 후보다 | REST 객체의 `node_id` 값(V2)으로 GraphQL 타입을 정한다 |
| Okta 이벤트 유형 JSON의 `targets` 스키마 (받아 둠) | G6. 감사 이벤트가 어떤 대상을 건드리는지 스키마 이름으로 말한다 | 대상 스키마의 속성 지문(V1)을 Management API 스키마와 맞춘다 |
| Salesforce Object Reference의 Refers To (받아 둠) | G3. 참조 대상 객체 | 명시 |
| 공식 SDK 타입 정의 (안 받음) | G1. Slack `@slack/web-api` 응답 타입은 실제 응답에서 만든 것이다. Okta, Google SDK 모델 | SDK 타입의 속성 지문을 IR 자리와 맞춘다 |
| 웹훅 명세의 `$ref` (GitHub 받아 둠) | G2 | 같은 `$ref`면 A4 |

**V7 실측.** 테넌트에서 실제 응답과 로그를 받아 값 겹침을 본다. 스키마로 닫히지 않는 질문(11절)과 G6을 닫는 유일한 길이다.

- 같은 대상의 REST 응답 값과 감사 로그 필드 값이 같으면 두 자리는 같은 공간이다(감사 `repo_id` = REST `repo.id`).
- Salesforce describe(`referenceTo`, `keyPrefix`), Atlassian `event-actions`(기계 action 키), Google `privileges.list`처럼 테넌트에서만 나오는 목록을 받는다.
- aegi-schema `data/slack_raw/`에 Slack 실측 응답이 이미 있다. 첫 검증 대상이다.

### 13.4 결정 규칙

각 가설(「자리 x는 공간 X다」, 「공간 X와 Y는 같다」)에 근거 집합을 단다.

| 등급 | 근거 |
| --- | --- |
| 명시 | `$ref`, Refers To, 판별자 표, GraphQL 필드 타입, 자기 설명 ID(V2) |
| 구조 | 왕복(A3), 구조 지문 정확히 같음(V1), 예시 왕복(V4) |
| 예시 | 희귀 예시 값 공출현(V3), 지문 부분집합(V1) |
| 사전 | 출처가 달린 사람의 한 줄 |
| 실측 | 테넌트 값 겹침(V7) |

1. 반대 근거(V5)가 하나라도 있으면 결정하지 않고 대기열로 보낸다. 실측만 반대 근거를 이긴다.
2. 명시나 구조 근거가 하나 있으면 결정한다.
3. 예시 근거는 서로 독립인 둘 이상이 있거나, 사전 한 줄과 함께 있을 때 결정한다.
4. 이름 유사도는 근거가 아니다. 후보 대기열에만 올린다.
5. 실측은 모든 등급을 확인하거나 뒤집는다. 뒤집힌 결정은 기록을 남긴다.

### 13.5 빈틈별 처리

| 빈틈 | 처리 |
| --- | --- |
| G1 예시만 있음 | 예시에서 구조를 만든다(이미 함). 키는 V2(패턴), 참조는 V3(공출현). SDK 타입(V6)을 받으면 구조와 타입을 바꿔 끼운다 |
| G2 인라인 | V1 지문으로 이름 있는 스키마에 대응. GitHub는 `node_id` 예시(V2)로 타입을 바로 안다 |
| G3 문자열 참조 | V3 공출현, V6 GraphQL 필드 타입, Refers To. 셋 다 없으면 참조 대상 미정으로 둔다. 필드 이름 꼬리(`_id`)로 정하지 않는다 |
| G4 다형 | 예시 값의 패턴(V2)이 둘 이상이면 다형. 판별자 역할 필드(`type`)의 예시 값과 대상 스키마는 사전 한 줄로만 잇는다 |
| G5 열린 맵 | 자리를 만들지 않는다. 「구멍」으로 남기고, 예시가 있으면 예시 구조를 「예시」 등급으로 넣는다 |
| G6 감사, 이벤트 | 감사 필드와 API 항목 사이는 문서만으로 결정하지 않는다. Okta는 `targets` 스키마 지문(V1, V6), GitHub와 Google은 실측(V7). Atlassian 표시 이름은 기계 키를 받기 전까지 감사 전용 후보로만 둔다 |
| G7 단건 조회 없음 | 목록 원소 키와 같은 컬렉션 단건 경로 위치(③ 목록 왕복). 그것도 없으면 「경로 단독」. 공간은 만들되 근거 없음 표시 |
| G8 출처 어긋남 | 출처마다 사실을 따로 두고 등급과 날짜를 단다. 덮어쓰지 않고, 어긋남은 대기열에 올린다 |

### 13.6 지금 구현에서 결정에 쓰고 있는 문자열 규칙

아래는 지금 결정에 쓰고 있다. 2부 기준으로는 후보 생성으로 내리거나, 비문자열 근거로 바꿔야 한다.

| 규칙 | 위치 | 바꿀 방향 |
| --- | --- | --- |
| 경로 파라미터 이름 꼬리 떼기와 앞 단어로 공간 이름 정하기 | `extract.py` `rest_param_space` | 경로 위치를 꼭짓점으로(1부 6절). 이름은 대표 이름에만 |
| 스키마 계열(접사 떼기, `-with-` 자르기, 낙타 표기 나누기) | `schema_spaces` | V1 구조 지문과 왕복 근거로 대체. 접사 결과는 후보 |
| 「바탕 이름으로 끝나면 같은 대상」 | `schema_spaces` `same()` | 왕복 근거가 있을 때만 |
| 필드 이름 꼬리 `_id`, `Id`로 참조 공간 정하기 | `space_of_name` | V3 공출현, V6 |
| 감사 action 이름 토큰 규칙 전부 (동사 사전, 명사 토큰, 이웃 토큰 붙이기, 공간 이름 + 명사) | `info_map.py` `audit_links`, `audit_space` | 감사 필드 값 근거(실측)로. 문서 단계 결과는 「후보」 등급으로만 표시 |
| 감사 category ↔ 공간 별칭, 감사 필드 이름 ↔ 항목 경로 | `audit_alias`, `fields`, `fields_change` | 출처 달린 사전은 유지. 필드 이름 같음은 실측으로 확인 |
| 필터 인자 이름 ↔ 응답 필드 이름 | `filters` | 같은 동작 안 같은 명명 체계라 오류가 작다. 예시 왕복(V4)이 있으면 결정, 없으면 후보 |

감사 연결은 거의 전부 이름 토큰에 기대고 있다. 문서만으로는 비문자열 근거가 거의 없어서(G6), 2부 기준으로 정직하게 쓰면 문서 단계의 감사 연결은 대부분 「후보」가 된다. 확정은 실측에서 한다.

## 17. GitHub node_id 해독 (2026-10-15)

`node_id` 값을 해독해 GraphQL 타입을 공간 근거로 넣었다(2부 V2). 가장 큰 효과는 반대 근거다. 기존 v2의 `user` 공간은 user, team, organization, enterprise 스키마 19개를 한 덩어리로 묶고 있었다. 「A 또는 B」 자리(다형 대안)를 같은 공간 근거로 썼기 때문이다. node_id 타입이 서로 다르면 합치지 않게 하자 이 덩어리가 풀렸다.

자료:

- `normalize_openapi.py`가 OpenAPI 3.1 `examples` 배열(스키마 속성 예시)을 `examples`에, 예시 응답(`components/examples`)의 값을 자리별 `samples`에 옮긴다. GitHub `node_id` 자리 2,126곳 중 1,862곳에 값이 생겼다
- 사전 `node_id_field: node_id` (github.yaml)

해독(`node_id_tag`). 값의 형식만 보고 이름은 비교하지 않는다:

| 형식 | 예 | 표지 |
| --- | --- | --- |
| 옛 형식 base64 `<길이>:<타입><DB id>` | `MDQ6VXNlcjE=` → `04:User1` | `User`, DB id `1` |
| 새 형식 `<접두사>_<msgpack>` | `U_kgDOAAAAAQ` | `U_` (약자 뜻은 쓰지 않는다) |

규칙:

1. 레코드 자리의 node_id 예시가 말하는 표지를 `gql:<표지>` 꼭짓점과 잇는다. 등급은 「예시」다. 이름 있는 스키마는 스키마 속성 예시만 보고, 인라인 레코드는 예시 응답 값도 본다
2. 다형 자리(한 자리에 스키마 여럿)는 표지를 달지 않는다. 대안들의 예시가 한 자리에 섞인다
3. 자기 일관성: 옛 형식 안의 DB id가 같은 레코드의 `id` 예시와 다르면 그 표지로 합치지 않고 반대 근거로만 쓴다. GitHub `enterprise.node_id` 예시가 `Repository1296269`(복사 오류)인 경우를 막는다
4. 한 공간은 한 타입이다. 합친 뒤 옛 형식 타입이나 새 형식 접두사가 둘이 되면 어느 간선이든(왕복, 지문, 다형 대안, 사전) 합치지 않는다
5. 약한 간선(node_id 예시, 다형 대안)은 각자 단건 조회 경로를 가진 두 동치류를 합치지 않는다. 서로 다른 컬렉션이다(issue와 pull-request, artifact와 check-suite)
6. 강한 간선부터 합친다(왕복, 지문, 그다음 다형 대안). 근거가 많은 꼭짓점이 타입 자리를 먼저 차지한다
7. 다형 자리는 구조 지문에서 뺀다. 대안들의 속성이 섞여 `enterprise`와 `simple-user`가 같은 지문이 되었다

결과 (GitHub, 앞은 17절 전 v2):

| 항목 | 전 → 후 |
| --- | --- |
| ID 공간 (경로 단독 제외) | 252 → 250 (전역 22 → 23, 범위 안 122 → 124, 스키마 전용 108 → 103) |
| 정보 항목 | 15,082 → 14,899 |
| 동작별 결정자 항목 | 2,036 → 1,946 |
| 참조 간선 | 222 → 256 |
| 감사 action 공간 연결 | 456 → 655 (team, org 별칭이 이제 자기 공간을 찾는다) |

나머지 provider는 결과가 그대로다(규칙 4~7은 반대 근거가 있어야 작동한다). v1 GitHub은 필드 행 순서가 바뀌어 타입이 둘인 `insecure_ssl` 항목 하나와 본문 관계 하나만 달라졌다.

한계:

- `repository`, `repository-webhooks`는 id 예시(42)와 node_id 안의 DB id(1296269)가 달라 반대 근거로만 쓰였다. 값 모양이 enterprise 복사 오류와 같아서 이름 없이는 구별할 수 없다. 실측(V7)으로 닫는다
- `workflow-run`이 `CheckSuite` 표지로 `simple-check-suite`와 합쳐졌다. 예시 등급이라 틀릴 수 있다
- 옛 형식 `User`와 새 형식 `U_`는 한 스키마에 둘 다 나올 때만 이어진다. 약자 표는 쓰지 않았다
- 같은 원칙(컬렉션이 다르면 다형 대안으로 합치지 않음)이 node_id 없는 provider에도 적용되지만, 지금 자료에서는 바뀐 것이 없다

## 18. GitHub GraphQL SDL (2026-10-15)

`normalize_github.py` 5단계가 GHEC GraphQL 스키마(`schema.docs.graphql`, 2026-10-13 받음)를 `ir/graphql_types.jsonl`로 옮긴다(`graphql_sdl.py`). 타입 1,824개: 객체 1,032(Node 구현 289), 입력 424, enum 257, 인터페이스 50, union 48, 스칼라 13. 필드 9,736개.

v2(`graphql()`)는 SDL을 node_id 표지로만 공간에 붙인다. 공간 이름과 GraphQL 타입 이름을 비교하지 않고, REST 필드 이름과 GraphQL 필드 이름도 맞추지 않는다.

| 쓰임 | 규칙 | GitHub 결과 |
| --- | --- | --- |
| 타입 확인 | node_id 표지가 SDL의 Node 구현 객체인가 | 17개 중 13개 확인. 옛 이름 4개(`Integration`은 SDL에서 `App`, `Gate`, `GateBranchPolicy`, `IssueEvent`)는 SDL에 없다 |
| 명시 참조 | 타입 T의 필드 타입 U가 다른 공간의 타입이면 참조 간선(`via: graphql`). 인터페이스와 union은 구현 타입 모두(`graphql_poly`). `XxxConnection`은 `nodes` 원소 타입으로 한 번 따라간다(Relay 규약) | 참조 92개. 참조 간선 256 → 289 |
| GraphQL로 읽히는 값 | 공간마다 스칼라와 enum 필드 목록(`graphql` 절) | 375개. repo 73, pull_request 67, user 50, org 47 |

한계: SDL은 node_id 표지가 붙은 공간에만 닿는다(250 중 17). `team`, `repository` 공간은 표지가 반대 근거로만 쓰여(17절) SDL이 붙지 않았다. SDL의 `databaseId`가 REST `id`와 같은 값인지는 실측으로 확인한다.
