# 정보 지도 설계 (초안)

작성 2026-10-13. 「오브젝트 후보 추출 설계.md」의 ID 공간(3.0)과 다리(3.2-b)를 이어받는다.

## 요약

- Object와 Relation으로 나누기 전에, 문서에서 얻을 수 있는 모든 정보가 서로 어떻게 연결되는지를 먼저 그린다. 이것이 정보 지도다.
- 지도는 타입 수준이다. 문서에는 인스턴스가 없으므로 「이 자리에는 어떤 종류의 정보가 들어가고, 그 정보는 무엇에 종속되는가」만 다룬다.
- 한 응답 안의 연결은 구조(같은 객체, 경로 파라미터)로 정한다.
- **서로 다른 응답과 로그 사이의 연결은 공통 닻을 통해서만 만든다.** 닻은 셋이다. ID 공간(무엇에 대한 정보인가), 동작(어떤 요청이 읽고 쓰는가), 스키마(같은 모양인가). 이름이 비슷하다는 이유만으로는 잇지 않는다.
- 지도가 완성되면 결정자별로 묶어 Object, Relation, Assignment, 사건을 만든다.

```
① 자리 수집     API 요청/응답, 로그, 이벤트, 권한 어휘의 모든 필드 자리
② 자리 안 연결   한 응답, 한 이벤트 안에서 종속과 포함을 긋는다
③ 자리 간 연결   닻(ID 공간, 동작, 스키마)으로 다른 출처의 자리를 같은 정보로 묶는다
④ 출처 간 의미   사본, 변경, 열람 권한, 파생 간선을 긋는다
⑤ 단위화        결정자별로 묶어 Object, Relation, Assignment, 사건으로 나눈다
```

---

## 1. 기본 단위: 자리와 정보 항목

| 단위 | 뜻 | 예 |
| --- | --- | --- |
| 자리 (slot) | 한 출처의 한 위치 | `api:GET /users/{id} → $.profile.email`, `audit:<action> → $.actor.email` |
| 정보 항목 (item) | 같은 정보를 담는 자리들의 묶음 | 「user 공간의 email」 |
| 결정자 (determinant) | 정보 항목을 결정하는 키 | user 공간 ID, `(app, team)` 조합, 사건 한 건 |

자리는 수집하면 그대로 생긴다. 정보 항목은 ②와 ③에서 자리를 묶어서 만든다. **정보 항목의 정체성은 「결정자와 의미」의 쌍이다.** 결정자가 다르면 이름이 같아도 다른 항목이다.

## 2. 간선 종류

| 간선 | 뜻 | 단계 | 단위화 때 쓰임 |
| --- | --- | --- | --- |
| 결정 | A가 정해지면 B가 하나로 정해진다 | ② ③ | property 경계 |
| 포함 | A가 B의 범위다 (경로상 부모) | ② | 키의 일부 (tenant, parent) |
| 같은 공간 | 두 ID 자리가 같은 ID 공간이다 | ② ③ | Object 경계 |
| 참조 | 값이 다른 ID 공간의 ID다 | ② | Relation 후보 |
| 사본 | 다른 항목의 값을 어느 시점에 복사해 담았다 | ④ | 현재 property가 아니라 관측 기록 |
| 변경 | 사건 종류가 이 항목이나 관계를 바꾼다 | ④ | 감사 범위, `audited_actions` |
| 열람 권한 | 권한 어휘가 이 자리를 읽거나 쓰게 해 준다 | ④ | `read_by`, `write_by` |
| 파생 | 다른 항목들로 계산된 값이다 | ④ | `basis: computed` |

결정과 포함은 섞지 않는다. `/teams/{t}/apps/{a}`에서 team은 app 설치의 범위(포함)이지, 설치 시각을 결정하는 값이 아니다. 설치 시각의 결정자는 `(app, team)` 조합이다.

## 3. 한 응답 안의 연결 (②)

한 응답 안에서는 구조가 신호다.

| 규칙 | 신호 | 간선 |
| --- | --- | --- |
| I1 | 같은 객체 안의 `id` class 필드와 그 형제 필드 | 형제는 그 id에 결정됨 |
| I2 | 경로 파라미터 | 응답 최상위 객체의 결정자에 포함됨 |
| I3 | 중첩 객체에 `id` class 필드가 있음 | 중첩 객체의 형제 필드는 바깥이 아니라 그 id에 결정됨 (사본 후보) |
| I4 | 배열 | 결정이 아니라 다대다. 배열 원소가 ID면 참조, 객체면 원소의 id가 결정자 |
| I5 | `ref` class 필드 | 참조 간선 |
| I6 | 응답에 없는 요청 맥락 (`$request`, 토큰의 테넌트) | 포함 간선 |
| I7 | 응답 최상위 배열 원소에 자기 키가 없고, 참조 이름(`*_id`, 사전 등록 이름)인 필드가 둘 이상 | 그 참조들의 조합이 결정자 (`role_assignments[*]` → @entity × role × user). 레코드 안의 테넌트 참조는 조합에 넣는다(I6 제외는 요청 맥락에만). 다형 참조(`entity_id`)는 `@이름` 한 자리. 자기 키: `id`, `ts`, 배열 이름을 딴 `*_id`(`active_sessions[*].session_id`), 사전 `record_key_alias` |
| I1b | `id`의 공간을 값으로 못 정함 (GitHub ID에는 접두사가 없다) | 그 객체의 응답 스키마 이름으로 공간을 정한다. 사전 `schema_space`, 아니면 접사(`simple-`, `full-` ...)를 뗀 이름이 이미 아는 공간일 때만 |
| I1c | 스키마 이름도 없음 (웹훅 payload 의 인라인 객체) | 객체를 담은 속성 이름으로 정한다 (`$.repository` → repo). 사전 `object_space` |
| I2c | REST 경로가 파라미터로 끝남 | 마지막 파라미터의 공간이 결정자, 앞 파라미터는 범위 (`/repos/{owner}/{repo}/issues/{issue_number}` → issue) |
| I2d | REST 경로가 단어로 끝남 | 마지막 ID 공간이 결정자 (`/issues/{issue_number}/lock` → issue) |
| I2e | 경로 끝 파라미터가 ID가 아님 (`branch`, `path`, `tag`) | 앞 공간 안의 이름 키 (repo 안의 branch) |
| I8 | 부모 공간 경로 아래의 목록 동작이 다른 공간의 레코드를 돌려줌 | 부모 × 원소 관계. 부모 쪽에 다중값 참조 항목을 둔다 (`/repos/{owner}/{repo}/collaborators` → repo의 `collaborators`, 원소 user) |

I3가 중요하다. 메시지 응답 안의 `user: { id, name }`에서 `name`은 메시지가 아니라 user ID에 결정된다. 메시지에 붙이면 같은 정보가 메시지마다 다른 property로 생긴다.

`id`라는 이름이 결정자를 보장하지 않는다. Okta `AppUser.id`는 사용자의 id다. id class 판정은 「오브젝트 후보 추출 설계」 3.1과 ID 공간 주인 규칙을 따른다.

## 4. 서로 다른 출처 사이의 연결 (③)

### 4.1 원칙

서로 다른 응답, 서로 다른 로그 이벤트의 자리를 잇는 방법은 하나다. **두 자리가 같은 결정자에 매달려 있음을 먼저 보이고, 그다음에 같은 의미임을 보인다.**

```
1단계  결정자가 같은가   →  ID 공간 연결 (다리 B1~B4)
2단계  의미가 같은가     →  아래 S1~S5
```

1단계를 건너뛰면 안 된다. `email`이라는 이름은 사용자 응답에도, 초대 응답에도, 감사 로그 actor에도 있다. 결정자가 각각 user, invite, 사건이면 다른 정보다.

### 4.2 결정자 맞추기

결정자 연결은 「오브젝트 후보 추출 설계」의 ID 공간 합치기(3.3)와 다리(B1~B4)를 그대로 쓴다.

| 다리 | 무엇으로 잇나 |
| --- | --- |
| B1 스키마 공유 | 같은 `$ref` 스키마 |
| B2 동작 연결 | 권한 어휘의 `op_ids`가 같은 동작을 가리킴 |
| B3 ID 모양 | ID 접두사 사전, 명세 예시 값의 접두사 |
| B4 이름 사전 | 사람이 관리하는 별칭 사전 |

로그의 대상이 ID가 아니라 이름 문자열일 때(GitHub 감사 로그의 `repo`)는 결정자가 「이름」이다. ID 공간과 이름이 일대일인지는 문서로 확인되는 경우에만 잇고, `name_key`로 표시한다.

### 4.3 의미 맞추기

결정자가 같은 두 자리를 같은 정보 항목으로 묶는 규칙이다. 위에서부터 쓴다.

| 규칙 | 신호 | 예 | 근거 등급 |
| --- | --- | --- | --- |
| S1 스키마 같은 경로 | 같은 스키마의 같은 필드 경로 | GitHub API와 웹훅이 같이 쓰는 `repository.visibility` | stated |
| S2 쓰기와 읽기 짝 | 같은 ID 공간의 쓰기 동작 요청 본문 경로와 읽기 동작 응답 경로가 같음 | `PATCH /users/{id}` 본문 `profile.email`과 `GET /users/{id}` 응답 `profile.email` | stated |
| 필터 | 조회 동작의 인자 이름이 그 동작 응답 필드 이름과 같음 | `admin.roles.listAssignments`의 `role_ids`와 `role_assignments[*].role_id` | structural |
| S3 목록과 단건 | 같은 공간의 list와 get이 같은 스키마를 씀 | 목록 원소와 단건 응답 | stated |
| S4 이름 정규화와 타입 | 결정자가 같고, 정규화한 이름과 값 타입(형식, enum 값 집합)이 같음 | 로그 `actor.email`과 사용자 응답 `email` | structural |
| S5 이름 사전 | 사람이 관리하는 필드 별칭 사전에 있음 | 로그 `alternateId`와 사용자 `login` | curated |

요청은 자리가 아니다. 우리가 보내는 값이지 SaaS가 돌려주는 상태가 아니다. 그래서 요청 본문과 조회 인자는 항목을 만들지 않고, 항목에 「쓰는 동작」과 「거르는 조회」를 붙이는 근거로만 쓴다(2026-10-14 구현).

- S2: 쓰기 동작의 대상은 그 동작 응답 최상위 객체의 결정자다(`POST /repos/{o}/{r}/issues`의 응답은 issue). 본문 경로가 그 대상의 응답 항목 경로와 같으면 그 항목을 쓴다. 응답의 같은 이름 자리가 다른 공간 객체면 관계 쓰기다(`issues/create`의 `assignees` → user). 둘 다 아니면 「쓰기만 되는 정보」로 남긴다
- 필터: 이름은 그대로, s를 뗀 것, `_ids` → `_id`로 비교한다. 인자가 객체 그릇(`assignee`, `labels`)과 맞으면 그 아래 값 필드(`name`, `login`, `id` ...)다. 가장 얕은 자리만 쓴다. 쪽 나누기와 정렬 인자(`common.yaml` `filter_skip`), 응답의 주인을 정하는 인자(I2), `id`는 뺀다. 인자와 필드의 공간이 다르면 대기열 `filter_space_conflict`

S4는 enum 값 집합이 다르면 묶지 않는다. 이름이 같아도 값 집합이 다르면 다른 정보일 가능성이 크다. 증거끼리 충돌하면 묶지 않고 대기열로 보낸다.

### 4.4 출처 간 의미 간선 (④)

같은 정보로 묶이지는 않지만 연결되는 경우가 있다. 로그와 이벤트에서 특히 많다.

**사본.** 로그와 이벤트 payload의 대상 필드는 대개 그 시점의 값을 복사한 것이다. 감사 로그 actor의 email은 그 사람의 현재 email이 아니라 사건 당시의 email이다.

- 판정: 자리의 결정자가 사건이고, S1~S5로 다른 ID 공간 항목과 의미가 같으면 사본 간선을 긋는다
- 단위화: 사건의 속성으로 남긴다. 대상 Object의 현재 property로 합치지 않는다

**변경.** 감사 로그 action과 이벤트 종류가 어느 정보 항목이나 관계를 바꾸는지다.

| 신호 | 예 | 근거 등급 |
| --- | --- | --- |
| action이 쓰기 동작과 이어짐 (문서가 대응을 명시) | 벤더가 「이 API 호출은 이 action을 남긴다」고 적은 경우 | stated |
| `details`에 이전 값과 새 값 자리가 있고, 그 자리가 S1~S5로 어떤 항목과 묶임 | `details.old_value`, `details.new_value` | structural |
| action 이름의 동사 쌍과 대상 둘 (「오브젝트 후보 추출 설계」 E4b) | `added`/`removed` → 관계 생성과 삭제 | structural |
| 위가 없고 action 이름만 있음 | | unknown. 대상 Object에만 연결 |

변경 간선이 모이면 「이 정보가 바뀔 때 로그가 남는가」를 항목마다 알 수 있다. 로그가 없는 항목은 탐지 공백 후보다.

**열람 권한.** 권한 어휘 → 동작(B2) → 그 동작의 요청과 응답 자리. 「어떤 권한을 가진 연동이 이 정보를 읽을 수 있는가」가 항목 단위로 나온다.

**파생.** 호출자 기준으로 계산되어 오는 값이다. GitHub 저장소 응답의 `permissions`처럼 호출한 사람에 따라 값이 바뀌는 자리는 저장소에 결정되지 않는다. 결정자는 `(저장소, 호출자)`이고 `basis: computed`다.

## 5. 단위화 (⑤)

정보 항목을 결정자별로 묶는다.

| 결정자 | 결과 |
| --- | --- |
| ID 공간 하나 | 그 공간의 Object와 property |
| ID 공간 둘 이상의 조합 | Relation. 독립 회수 가능하면 Assignment Object (Interface_Spec 기준) |
| 사건 한 건 | 사건 기록. 사본 간선이 걸린 값은 사건 속성 |
| 결정자 + 호출자 | computed 관계 |
| 결정자를 못 정함 | 대기열 |

이 결과는 「오브젝트 후보 추출 설계」의 후보와 같은 모양이다. 차이는 후보 하나마다 property 목록, 출처 자리, 변경 사건, 열람 권한이 같이 붙어 나온다는 점이다.

## 6. 근거 등급

모든 간선에 등급을 단다.

| 등급 | 뜻 |
| --- | --- |
| stated | 명세나 카탈로그가 구조로 명시함 (같은 스키마, 쓰기와 읽기 짝, 벤더 대응표) |
| structural | 구조 신호로 추정함 (같은 객체 안, 이름과 타입 일치) |
| curated | 사람이 관리하는 사전에 의함 |
| unknown | 정할 수 없음. 간선을 긋지 않고 대기열에 넣음 |

문서에는 인스턴스가 없으므로 structural 간선은 실측 응답이 들어온 뒤 검증 대상이다. 실측 값으로 결정 간선이 깨지면(같은 결정자에 값이 둘) 그 간선을 내린다.

## 7. 문서만으로 못 하는 것

- 감사 로그 `details`가 열린 맵이면 변경 간선을 structural 이상으로 못 올린다.
- 이름 문자열이 결정자인 로그(GitHub `repo`)는 이름 변경 전후의 연결을 문서로 정할 수 없다.
- 같은 이름, 같은 타입인데 의미가 다른 자리(예: 두 `status`)는 S4로 묶일 위험이 있다. S4는 결정자가 같을 때만 쓰고, 그래도 충돌하면 대기열이다.

### 감사 action → 정보 항목 (2026-10-13 추가)

Slack 감사 action 문서는 action마다 설명 한 줄만 주고 `details` 구조를 주지 않는다. 그래서 action 이름 토큰만으로 잇는다(규칙은 설명문을 읽지 않는다). 사전은 `lexicons/common.yaml`의 `action_effect`, `action_verb_lemma`, `action_stop_tokens`와 `lexicons/slack.yaml`의 `action_token_alias`다.

1. category를 공간에 잇는다 (기존 `audit_alias`)
2. 이름의 첫 동사 토큰으로 효과를 정한다: 속성 변경, 관계 변경, 생성과 삭제, 사용 기록
3. `by` 뒤는 행위자라 버린다. `from` 뒤가 공간이 아니면 출처 표시라 버린다
4. 관계 변경: 이름에 다른 공간 토큰이 있으면 두 공간 사이의 다중값 참조 항목(배열) 중 가장 얕은 것
5. 속성 변경: 명사 토큰이 경로 토큰에 다 들어가는 항목. 명사가 그릇 이름이면(`profile`) 그릇 아래 전부
6. 생성과 삭제: 동사가 뒤집는 상태 항목과 이름이 정확히 같으면 그 항목(`deactivated` → `deleted`, `archive` → `is_archived`). 아니면 명사가 없거나 이미 아는 종류 표시일 때 대상 자체, 모르는 명사면 지도에 없는 대상
7. 쓰기 동작 경유: 같은 공간에 쓰는 동작 중 동사 원형이 같은 것. 흔한 동사는 동작 줄기가 명사와 맞아야 한다

| --- | --- | --- | --- | --- | --- | --- |
| 속성 변경 216 | 32 | 58 | 1 | | | 125 |
| 관계 변경 27 | 17 | 4 | | | | 6 |

맞게 나온 예: `user_email_updated` → `email`, `role_change_to_admin` → `is_admin`, `user_deactivated` → `deleted`, `user_channel_join` → channel `members`, `user_added_to_usergroup` → subteam `users`, `public_channel_converted_to_private` → `is_private`, `app_scopes_expanded` → `scopes`, `user_profile_updated` → `profile.*`.

「지도에 없는 대상」 36건은 API 응답에 없고 감사 로그에만 보이는 하위 대상이다. 예: passkey, 채널 이메일 주소, 파일 공개 링크, 인증 정책, IdP 설정, EKM. Object 후보 쪽 `audit_only`와 같은 신호다.

- 감사 필드 목록이 action마다 있다. Slack에는 없던 근거다.
  - 변경 전후 짝(`previous_X`, `old_X`, `new_X`, `X_was`)이 있으면 X가 바뀐 항목이다. `repo.access` → `visibility`(`previous_visibility`), `repo.rename` → `name`, `team.update_repository_permission` → `permission`, `hook.events_changed` → `events`

## 10. 남은 질문

- 정보 항목의 「의미」를 이름 정규화 말고 무엇으로 표현할지. 값 타입과 enum 집합까지인지, 설명문을 쓸지. 현재 원칙은 규칙이 설명문을 읽지 않는 것이다.
- 사본 간선을 사건 속성으로 둘 때, 사건 쪽 규격(감사 로그 행 모양)이 aegi-schema에 따로 필요한지.
- 지도 저장 형식. 자리와 항목과 간선을 별도 표로 둘지, 후보 카탈로그에 붙일지.
