## 요약

- 기존 자료의 포함 오브젝트 281건 중 247건이 공간에 닿았다. 안 닿은 34건 중 진짜 누락은 9건이다. 13건은 대조 방법의 한계이고, 12건은 지도 규칙이 부모의 속성으로 둔 것이다.
- Cartography 노드 70종 중 65종은 API로 수집한다. 이 중 60종이 후보 공간에 닿았다. 못 닿은 5종 중 누락은 3종(Jira 테넌트, GitHub 도메인, 의존성 매니페스트)이다. 2종(언어, 의존성)은 자기 id가 없는 값이다. 나머지 5종은 파일 내용을 파싱하거나 설정값을 쪼개 만든 노드라 API ID 공간과 비교할 대상이 아니다.
- 진짜 누락은 원인별로 다섯 가지다.
  1. 수집하지 않은 명세: Okta Access Requests API
  2. 읽기 API가 없는 대상: Slack 토큰 4종, trigger
  3. GET만 있는 단일 자원을 공간에서 뺀 규칙: Jira 테넌트, Okta SSF stream (Okta ASA 설정, Google 설정은 부모의 속성으로 남음)
  4. GraphQL 전용 key_only 제외 규칙: GitHub 도메인, 의존성 매니페스트
  5. 부모 안 키로만 보이는 전역 대상: Google OAuth 앱(client_id)
- 조사 중 지도 오류 하나를 찾았다. Jira에서 페이지 봉투(PageBean) 64개가 Jev 키 공간 하나로 합쳐졌다. 2단계(중복 조사) 전에 고쳐야 한다.
- Confluence는 Cartography 모듈이 없어 기준이 없다. Jira와 Salesforce는 Cartography 노드가 각각 6종, 7종뿐이라 권한 핵심만 확인했다.

| 기준 | 범위 | 무엇 |
| --- | --- | --- |
| 기존 자료 | GitHub, Okta, Slack, Google Workspace | `aegi-schema/data/AEGI_Object_List_Final_2026-09-20.xlsx`의 Final_Reconciliation 중 최종 판정 「포함」 281건과 근거 API |

### 1.2 오브젝트와 공간을 잇는 방법

이름을 비교하지 않는다. 오브젝트의 근거 API를 IR 동작에 맞추고, 그 동작이 고르는 위치나 돌려주는 모양의 공간을 본다.

| 표면 | 맞추는 기준 |
| --- | --- |
| REST | 메서드와 경로 틀. 글자 조각이 같고 `{}`는 `{}`끼리. 이번에 「길이까지 같은 틀을 먼저」 규칙을 더했다. 이전에는 `GET /users/{username}`이 `.../users/{user_id}`로 끝나는 다른 API에도 붙었다 |
| Slack, Google | 메서드 id(`users.list`, `directory.users.list`) |
| GitHub GraphQL | SDL 타입 이름 |
| Salesforce | sObject API 이름 |

닿는 순서는 위치(단건 경로의 마지막 `{}`), relation이나 부모 안 레코드, 응답 모양, 래퍼 안 한 단계 박힌 레코드다.

## 3. 진짜 누락

### 3.1 수집하지 않은 명세

| SaaS | 오브젝트 | 근거 API | 원인 |
| --- | --- | --- | --- |
| Okta | request-type-full | `GET /governance/api/v1/request-types/{requestTypeId}` | 받은 IGA 명세(`okta_iga_openapi`, 동작 114개)에 Access Requests 부분이 없다 |
| Okta | rcar-entry-get | `GET /governance/api/v2/catalogs/default/entries/{entryId}` | 같음 |
| Okta | request-condition-full | `GET /governance/api/v2/resources/{resourceId}/request-conditions/{id}` | 같음 |

조치: Okta Identity Governance의 Access Requests v1, v2 명세를 수집 대상에 더한다.

### 3.2 읽기 API가 없는 대상

| SaaS | 오브젝트 | 왜 공간이 없나 |
| --- | --- | --- |
| Slack | app-token, bot-token, user-token | 발급 응답(`oauth.v2.access`)에 한 번 나오고 다시 조회하는 API가 없다. 감사 로그 이벤트로만 흔적이 남는다 |
| Slack | app-configuration-token | `apps.manifest.export`의 권한일 뿐 토큰 자체를 돌려주는 API가 없다 |
| Slack | trigger | Web API가 없다. Deno SDK와 워크플로 빌더에서만 다룬다 |

API 명세에서 ID 공간을 만드는 방식으로는 원리상 잡을 수 없다. 감사 이벤트 카탈로그(`catalog:audit`)에서 대상 종류로 올리거나 수동으로 등록해야 한다. 5절의 결정 항목이다.

### 3.3 GET만 있는 단일 자원을 공간에서 뺀 규칙

루프 17에서 「부모 아래 단일 자원은 POST나 DELETE가 있을 때만 공간」으로 정했다. GET, PUT만 있으면 늘 있는 설정이라 부모 공간의 속성으로 붙는다. 이 규칙 때문에 빠진 것이다.

| SaaS | 오브젝트 | 근거 API | 지금 위치 |
| --- | --- | --- | --- |
| Jira | 테넌트 (Cartography `JiraTenant`) | `GET /rest/api/3/serverInfo` | 공간 없음. 뿌리 경로라 붙을 부모도 없다 |
| Okta | stream | `GET /api/v1/ssf/stream` | 같음 |
| Okta | TeamSettings, PasswordPolicy, ActiveDirectoryPasswordPolicy | ASA `GET /v1/teams/{team_name}/settings` 등 | 팀, 프로젝트 공간의 속성 |
| Google | SecuritySettings | `cloudidentity.groups.getSecuritySettings` | 그룹 공간의 속성 |
| Google | AutoForwarding, ImapSettings | `gmail.users.settings.getAutoForwarding`, `getImap` | 사용자 공간의 속성 |
| Google | DomainVerificationToken | `gmailpostmastertools.domains.getVerificationToken` | 도메인 공간의 속성 |
| Google | LabelLock | `drivelabels.labels.locks.list` | 목록만 있고 단건 GET이 없다. 라벨 공간의 속성 |

이 중 성격이 다른 두 가지가 섞여 있다.

- **뿌리 단일 자원**(Jira serverInfo, Okta SSF stream): 테넌트 하나에 하나뿐인 대상이다. 부모가 없어 속성으로도 붙지 못하고 고아가 된다. 뿌리 단일 자원은 쓰기 동작이 없어도 singleton 공간으로 두는 것이 맞아 보인다. Okta 조직(`OrgSetting`)은 PUT이 있어 이미 singleton이다.
- **부모 아래 설정**(나머지): 기존 자료는 Policy로 포함했다. LabelLock은 단일 자원이 아니라 목록 원소지만, 단건 읽기가 없어 같은 처지다. 오브젝트로 올릴지, 부모의 속성으로 둘지는 interface 판정(3단계)에서 정하는 것이 맞다. 지금 지도에서는 부모 공간의 정보 항목으로 남아 있어 정보는 잃지 않는다.

### 3.4 GraphQL 전용 대상이 key_only 제외 규칙에 걸림

루프 18에서 「GraphQL의 key_only 공간은 REST나 RPC 응답, 후보 공간 참조로 닿을 때만 후보」로 정했다. REST에 같은 대상이 없으면 후보에서 빠진다.

| Cartography 노드 | GraphQL 타입 | REST 대응 | 판단 |
| --- | --- | --- | --- |
| `GitHubOrganizationDomain` | `VerifiableDomain` | 조직용 REST 없음 | 누락. 도메인 검증은 SSO와 메일 정책의 근거라 오브젝트 후보다 |
| `GitHubDependencyGraphManifest` | `DependencyGraphManifest` | SBOM은 문서 하나로 돌려주고 매니페스트 id가 없다 | 누락 후보. 공급망 시나리오가 범위에 들어오면 필요 |
| `ProgrammingLanguage` | `Language` | `GET /repos/{o}/{r}/languages`는 이름과 바이트 수 | 언어 이름은 값이다. 오브젝트가 아니다 |
| `GitHubDependency` | `DependencyGraphDependency` | 없음 | 타입에 자기 id가 없다. Cartography가 id를 합성한다 |

조치 후보: GraphQL `Node` 인터페이스(전역 `id`)를 구현한 타입은 REST 대응이 없을 때 후보로 둔다. 규칙이 원문 선언(`implements Node`)에 기대므로 이름 비교가 아니다.

### 3.5 부모 안 키로만 보이는 전역 대상

| Cartography 노드 | Cartography id | 우리 지도 |
| --- | --- | --- |
| `GoogleWorkspaceOAuthApp` | `client_id`, 테넌트 전체에 하나 | `Token`(local). `users/{userKey}/tokens/{clientId}`의 부모 안 키 |

Google Directory API에는 OAuth 앱을 직접 읽는 API가 없다. 사용자별 토큰 목록에서만 `clientId`가 보인다. 그래서 지도는 「사용자 안의 토큰」만 만들고 앱 자체는 만들지 않았다. 그러나 `clientId`는 사용자가 달라도 같은 앱을 가리키는 전역 값이다. 같은 값이 다른 부모 아래에서 반복되면 부모 밖 공간으로 올리는 규칙이 필요하다(값 정체성 규칙의 확장). 토큰은 사용자 × 앱 relation이 된다.

| Okta | team, Application, EmailDomainResponse, PolicyRule, WorkloadRole | `Application`, `PolicyRule`, `EmailDomainResponseWithEmbedded` 등 | 근거 API 칸이 비었다. team과 WorkloadRole은 ASA, OPA 쪽 대상으로 따로 확인이 필요하다 |

메서드를 붙여 다시 맞추면 GitHub 4건과 Google 4건 모두 공간에 닿는다(직접 확인함). Okta 5건은 근거 API를 채워야 정확히 판단할 수 있다.

### 4.2 Slack enterprise, permission, workflow-permission

- enterprise: `auth.test` 응답의 `enterprise_id` 필드로만 보인다. 지도에서는 속성 항목이다. Cartography에도 노드가 없다. Enterprise Grid를 범위에 넣을 때 다시 본다.
- permission, workflow-permission: `admin.apps.permissions.list`, `admin.workflows.permissions.lookup`의 응답이다. 자기 식별자가 없는 설정 묶음이라 앱이나 워크플로의 속성으로 붙었다. 3.3절의 「부모 아래 설정」과 같은 종류다.

## 5. Cartography와 모양이 다른 것

누락은 아니지만 2단계 이후 판단에 쓰일 차이다.

| Cartography 노드 | 우리 지도 | 차이 |
| --- | --- | --- |
| `SlackBot` (users.list의 봇 회원, U...) | 회원 공간 + 따로 `200.bot` (B...) | Slack에는 봇 사용자 id와 봇 id가 따로 있다. Cartography는 사용자 id만 쓴다 |
| `GitHubRulesetRule` | `repository-ruleset` 안 | 규칙에는 자기 id가 없다. Cartography가 id를 합성한다 |
| `GitHubContainerImage`, `Tag` | `package-version` | Cartography는 이미지 digest(레지스트리)로, 우리는 GitHub 패키지 버전 id로 본다. 다른 ID 공간이다 |
| `GitHubContainerImageLayer`, `GitHubAction`, `GitHubCodeOwnerRule`, `PythonLibrary`, `ReplyUri` | 없음 | 레지스트리 매니페스트, 워크플로 파일, CODEOWNERS 파일, lockfile, 앱 설정값을 파싱해 만든 노드다. API ID 공간이 아니다 |
| `OktaUserRole`, `OktaGroupRole` | 둘 다 `CustomRole`(local) | Cartography는 받는 쪽(사용자, 그룹)으로 나눴다. 우리는 역할 할당 하나의 공간이다 |
| `JiraPermissionGrant` | `PermissionScheme` 응답 안 `PermissionGrant` | 같은 대상. Cartography는 scheme 응답에서 꺼낸다 |

## 6. 2단계로 넘길 관찰

## 8. 한계

- Cartography 노드의 수집 API는 intel 코드를 읽고 손으로 적었다. 노드마다 근거 파일을 남겼지만, 한 노드가 여러 API를 섞어 쓰는 경우 대표 API만 적었다.

- 이번 조사는 「빠진 것」만 본다. 공간이 오브젝트가 될 수 없는 경우(불필요)는 interface 판정 단계에서 본다.

### 9.1 D3: Slack 감사 이벤트를 API로 읽을 수 있나

읽을 수 있다. Slack Audit Logs API(`https://api.slack.com/audit/v1/`)는 요청해서 가져오는 REST API다. 스트리밍이 아니다. Enterprise 조직에서 조직 소유자가 설치한 앱의 `auditlogs:read` 토큰으로 부른다. 우리 테넌트에서 2026-09-17에 이미 세 가지를 받았다(`aegi-schema/data/slack_raw/`).

| 엔드포인트 | 무엇 | 받은 것 |
| --- | --- | --- |
| `GET /schemas` | 감사 대상(entity) 종류와 각 필드 | 19종 |
| `GET /actions` | 행위 이름 목록 | IR의 감사 카탈로그 773개 |
| `GET /logs` | 실제 기록 | 201건 |

그러나 토큰과 trigger는 감사 기록에서도 자기 id로 나오지 않는다.

- entity 19종에 토큰과 trigger가 없다: workspace, enterprise, user, file, channel, app, workflow, usergroup, barrier, message, role, account_type_role, canvas, workflow_v2, template, legal_hold_policy, work_object_record (user와 app은 두 번 나온다).
- 토큰 행위(`bot_token_upgraded` 등)의 대상은 `app`이다.
- trigger는 `workflow_v2` entity의 필드(`trigger_name`, `trigger_channels`, `trigger_configuration`)로만 나온다.

그래서 D3는 「감사 카탈로그에서 공간으로 올린다」가 아니라 「앱과 워크플로의 속성으로 둔다」로 바꿨다.

대신 entity 19종은 Slack 대상 목록을 대조할 새 기준이 됐다. 우리 공간과 맞춰 본 결과다.

## 11. Slack enterprise (2026-10-18)

4.2절에서 enterprise를 속성으로 둔 판단은 틀렸다. enterprise는 Slack의 최상위 대상이다. 공간이 없었던 이유는 지도 규칙에 있었다.

- 지도는 「그 id를 자기 키로 가진 레코드」가 있어야 공간을 만든다(단건 읽기, 목록, 원문 키 선언, Jev 키).
- Slack에는 enterprise를 돌려주는 메서드가 없다. `E...` id는 다른 레코드의 필드로만 나온다: `objs_team.enterprise_id`, `objs_enterprise_user.enterprise_id`, `objs_conversation.enterprise_id`, `migration.exchange`.
- 원문 ID 형식 `defs_enterprise_id`(`^[E][A-Z0-9]{8,}$`)는 있었지만 자기 키에 붙은 곳이 없어 공간이 되지 못했고, 이 필드들은 「대상 모름」 참조였다.

고친 것

| 규칙 | 내용 | 결과 |
| --- | --- | --- |
| 참조로만 쓰이는 ID 형식 | 접두사가 있는 원문 ID 형식이 어느 레코드의 자기 키도 아니고 참조 필드에만 붙으면, 그 형식을 공간(꼴 ref_only)으로 세운다. 접두사 집합이 같은 형식이 이미 공간에 있으면 세우지 않는다 | Slack 3개: `defs_enterprise_id`(enterprise), `defs_app_id`(앱 id `A...`), `defs_group_id`(구형 비공개 채널 `G...`) |
| 형식을 가리키는 원문 참조 | 원문 참조가 모양이 아니라 ID 형식을 가리키면(`to.id_format`) 그 형식의 공간을 대상으로 정한다. 지금까지는 모양을 가리키는 참조만 풀고 있었다 | Slack 참조 116개의 대상이 정해졌다. 예: `auth.test`의 `team_id`, `user_id`, `bot_id` |

enterprise가 team의 상위라는 것은 `objs_team.enterprise_id` 참조로 드러난다. 소속 relation(team이 enterprise에 속함)은 2단계에서 확인한다. `defs_app_id`는 앱 레코드 공간(`200.approved_apps[*].app` 등)과 같은 대상일 수 있어 2단계 중복 후보다.

대조 스크립트도 참조로만 있는 공간을 세도록 고쳤다. 다만 확정 목록의 enterprise 근거(`auth.test`)는 문서 예시에 `enterprise_id`가 없어, 대조에서는 `auth.test` 응답이 만든 다른 relation(봇 × 사용자 × 팀)에 닿은 것으로 잡혔다. 실제 enterprise 공간은 `defs_enterprise_id`다.

## 12. 복합키 오브젝트 기준 R0~R2 (2026-10-18)

D3에서 Slack 토큰을 속성으로 둔 판단은 aegi-schema와 맞지 않았다. interface는 Object의 태그이자 계약이라 속성은 Credential이 될 수 없고, 대시보드 피해범위(`detection/v2/blastRadius.ts`)는 `objectsByInterface('Credential')`에서 출발한다. Slack 봇 토큰과 incoming webhook이 시나리오 B의 출발점이다.

aegi-schema는 Assignment(관계 자신, 어떤 relation의 끝점도 아님)와 Credential(끝점, template 출발 3, 도착 3)을 나눈다. 그래서 ID × ID 레코드를 다음 순서로 판정한다.

| 단계 | 조건 | 결과 |
| --- | --- | --- |
| R0 | 자기 id가 있다 | ID 공간 |
| R1 | 자기 id 없이 다른 공간 id들의 조합이 키다 | relation (Assignment) |
| R2a | 자격증명 값을 담는다 | 복합키 오브젝트 (Credential 계약을 행에 붙인다) |
| R2b | 키 밖의 세 번째 공간을 가리킨다 | 복합키 오브젝트 (끝점) |
| R2c | 다른 레코드가 이 레코드를 가리킨다 | 복합키 오브젝트 (끝점) |

이번에 지도에 넣은 것은 R2a다(`map3.composite_credentials`).

- 자격증명 값 판정: aegi-schema 「항상 감추는 값」의 필드 이름(`access_token`, `refresh_token`, `client_secret`, `signing_secret`, `verification_token`, `bot_access_token`, `app_token`, `api_token`, `sharedSecret`, `privateKeyData`)과 값 모양(`xox` 토큰, `xapp-`, `hooks.slack.com` 주소). 이름 규칙과 값 규칙을 따로 세어 대조한다(`verify.credential_material`). JWK의 `n`, `e`, `x5c`는 공개키 부분이 섞여 빼었다. 웹훅은 원문 예시에 `/services/`가 없는 주소가 있어 호스트로 본다.
- 값을 담은 레코드나 그 위 레코드가 자기 id 공간의 단건 응답이면(R0) 그 오브젝트의 자재로 표시만 한다(`credential_material`).
- 아니면 자리마다 오브젝트 하나(꼴 composite_key). 키는 위쪽 레코드와 담은 레코드가 가리키는 공간들, 인증 대상(R2b)은 담은 레코드가 직접 가리키는 공간들. 값의 접두사(`xoxb`, `xoxp`, `xoxe` 등)를 남긴다.

결과

| provider | 이름과 값 둘 다 | 이름만 | 값만 | 새 오브젝트 | 기존 오브젝트에 표시 |
| --- | --- | --- | --- | --- | --- |
| Slack | 9 | 3 | 4 | 16 | 0 |
| GitHub | 0 | 1 | 0 | 1 | 0 |
| Okta | 0 | 44 | 0 | 8 | 36 (Client, IdentityProvider, OAuth2ClientSecret, ProjectCloudAccount) |

Slack 16개는 봇 토큰 2, 사용자 토큰 6, 앱 설정 토큰 2, incoming webhook 1, 갱신 토큰 2, 앱 비밀값 3이다. 같은 종류가 여러 동작에서 나와 겹치므로 2단계에서 접두사와 키로 묶는다. 기존 자료 대조는 Slack 23 → 25/30(bot-token, user-token).

한계

- 키가 빈 오브젝트가 많다. 문서 예시의 참조 대상이 안 정해진 경우다(구형 `oauth.access`, `tooling.tokens.rotate`, Okta 토큰 발급 응답).
- 키가 틀리게 잡힌 것: GitHub App client secret(앱 주인으로), Okta API 서비스 통합 비밀값(`AgentJsonWebKeyECResponse`로).
- 사용자 토큰의 인증 대상(R2b)은 예시 값(`U1234`)이 원문 사용자 id 형식보다 짧아 못 정했다.
- R2b, R2c는 아직 지도에 넣지 않았다. 2단계 relation 조사와 같은 재료를 쓴다.
- Slack app-token(`xapp-`)은 어느 응답에도 값이 없어 R2a로도 못 만든다. trigger는 자동화라 이 기준 밖이다.
- Okta AppUser는 `credentials.userName`과 비밀번호 자리가 있지만 이름이 목록에 없어 R2a가 걸리지 않았다(판단표 R2).

### 12.1 복합키 재료 고침 (2026-10-18)

복합키는 이렇게 만든다(`map3.composite_credentials`, 결과는 공간의 `key_fields`).

1. 값을 담은 레코드의 자리 중 다른 공간을 가리키는 것: 참조, 자기 키, 공간에 속한 박힌 레코드.
2. 그 위 레코드들의 같은 자리(맥락: 앱, 팀). 같은 공간을 가리키는 자리가 1에 있으면 1만 쓴다. 사용자 토큰의 사용자는 `authed_user.id`이고 위 레코드의 `bot_user_id`가 아니다.
3. 동작 경로의 위치 공간.
4. 자격증명 값을 직접 담은 박힌 레코드는 넣지 않는다. 다른 자격증명의 자리다(봇 토큰의 키에 `authed_user`를 넣지 않는다).

자리가 가리키는 공간은 다음 넷 중 하나로 정한다.

| 근거 | 등급 | 이번에 더한 것 |
| --- | --- | --- |
| 원문 참조 | stated | |
| 예시 값이 원문 ID 형식 하나에 모두 맞음 | example | 조합 레코드 부분 필드에서만 쓰던 규칙을 모든 필드로 넓혔다. Slack 185개 자리의 대상이 정해졌다(예: `oauth.access`의 `team_id`) |
| Jev Choice: 「이 필드는 어느 공간의 id인가」 (선택지는 원문 ID 형식이 있는 공간과 역할 목록, 그리고 none) | model | Slack 25개 필드. 0.7 이상만 쓴다. 예: `tooling.tokens.rotate`의 `team_id` → 팀 0.76, `user_id` → 사용자 0.99, `oauth.access`의 `bot.bot_user_id` → 봇 0.81. `incoming_webhook.channel`은 0.53이라 쓰지 않았다(값이 채널 이름) |
| 박힌 레코드의 소속 | 구조 | |

틀린 키 두 개의 원인과 처리

| 대상 | 원인 | 처리 |
| --- | --- | --- |
| GitHub App client secret | 매니페스트 변환 응답이 원문 allOf로 `integration`과 같은데, R0 판정이 단건 위치가 돌려주는 모양만 봤다 | R0을 넓혔다: 원문(allOf, 키 선언)이나 변환(왕복) 근거로 단건 위치가 있는 공간에 합쳐진 모양도 그 오브젝트다. 예시 값 쌍이나 지문만으로 합쳐진 모양은 아니다. 지금은 `integration`의 자재로 표시 |

남은 키 없음 6개: Slack 토큰 회전 응답 2(G8 사용자 토큰을 회전한 결과), Sign in with Slack 토큰 1(팀과 사용자가 `id_token` JWT 안에만 있다), Okta 토큰 발급 응답 4(Okta는 갱신 토큰을 `OAuth2RefreshToken` 공간으로 따로 가진다). 응답에 id 자리가 없어 규칙으로는 못 만든다. 2단계에서 같은 종류의 오브젝트와 묶거나 발급 응답으로 보고 뺀다.

확인 필요: `oauth.v2.access`의 `enterprise`가 enterprise 공간이 아니라 팀 공간(`objs_team`)으로 잡혔다. 앞선 루프의 공간 합침에서 온 것이라 2단계 중복 조사에서 본다.

### 13.5 넘기는 과제

- 수집: Slack `workflows.triggers.list`와 `admin.workflows.permissions.lookup` 응답 모양, 앱 수준 토큰 회전 API 확인, Okta SSF stream 이외 선택 인자 위치 점검

### 13.6 사용자 결정 (2026-10-18)

13.4의 세 질문을 모두 권고대로 정했다.

1. 복합키 자격증명의 한 행 = 설치 × 자격증명 종류. 토큰 인스턴스와 회전은 그 행의 상태와 이력으로 둔다.
2. Okta 앱 비밀값과 API 서비스 통합 비밀값은 같은 ID 공간(`OAuth2ClientSecret`)으로 두고, 부모 두 종류(`apps/{}`, `api-services/{}`)를 구분해 기록한다. 근거가 약하다는 점(지문, 예시 값 쌍)을 남긴다.
3. GitHub Action, CODEOWNERS 같은 파생 노드는 수집 과제로 두고 v1 고정에 넣지 않는다.

1단계는 여기서 닫는다.
