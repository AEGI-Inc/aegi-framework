1. 개요: AEGI Multi-SaaS Adapter의 목적과 필요성

현대 기업 환경에서 업무 인프라는 온프레미스 서버 중심에서 클라우드 SaaS(Software as a Service) 환경으로 완전히 전환되었습니다. 기업은 소스코드를 GitHub에 보관하고, 의사소통은 Slack에서 수행하며, 문서와 드라이브는 Google Workspace에, 프로젝트와 이슈는 Jira/Confluence에, 고객 영업 정보는 Salesforce에, 그리고 이 모든 시스템의 중앙 로그인은 Okta로 통합 관리합니다.

왜 Multi-SaaS Adapter가 필요한가? (문제 정의)

각 SaaS는 저마다 완전히 다른 인증 표준(OAuth 2.0 PKCE, 3LO, DPoP, DWD, API Token), 데이터 포맷(REST, GraphQL, SOQL), 그리고 독자적인 사용자/권한 모델(RBAC, 권한셋, 세션 정책)을 가지고 있습니다. 이로 인해 단일 SaaS 보안 도구로는 "특정 임직원 1명이 여러 SaaS에 걸쳐 어떤 최종 접근 권한(Effective Access)을 가지는지", 그리고 "한 계정이 탈취되었을 때 침해 사고가 어디까지 번져나가는지(Blast Radius)"를 파악하는 것이 불가능합니다.

AEGI Multi-SaaS Adapter는 6개 주요 SaaS의 설정값, 계정, 역할, 권한 체계, 자격증명 수명주기, 그리고 감사 로그(Audit Logs)를 별도의 에이전트 설치 없이(Agentless) 공식 읽기 전용 API를 통해 주기적으로 수집하여 중앙 보안 그래프 모델로 변환하는 핵심 수집 엔진입니다.

2. 수집기(Adapter) 아키텍처 및 4단계 처리 파이프라인

수집기는 독립 실행형(Standalone) 데모 환경 및 분산 클라우드 환경에서 동일하게 구동될 수 있도록 4단계 직렬 파이프라인(Collect ➔ Normalize ➔ Identity Link ➔ Evaluate)으로 구현되어 있습니다.

STAGE 01
수집 (Collect)
SaaS별 읽기 전용 REST / GraphQL API 호출.
Rate-limit 대응, 자동 페이지네이션, 서킷 브레이커.
STAGE 02
정규화 (Normalize)
SaaS별 이종 JSON을 통합 객체 모델(계정, 역할, 리소스, 자격증명)로 매핑.
STAGE 03
동일인 신원 연결
이메일, SCIM, Okta SSO 연동 이력을 바탕으로 각 SaaS의 계정을 자연인 1명에 바인딩.
STAGE 04
위협 판정 및 게시
유효 권한 계산, 계정 탈취 피해 반경 산출, ISMS-P/ISO 27001 컴플라이언스 평가.
수집 엔진 핵심 설계 특성
  • 지능형 서킷 브레이커 (Circuit Breaker): 고객 테넌트에 미구독된 유료 애드온(예: Okta OIG, Atlassian Guard) 엔드포인트 호출 시 연속 5회 권한 거부(401/403) 발생 시 해당 카테고리를 자동으로 건너뛰어 API 할당량(Rate Limit)을 보존합니다.
  • 계층적 의존성 검사 (Dependency Guard): 상위 부모 리소스(예: GitHub 저장소 0개, Slack 봇 0개)가 없으면 하위 의존 API를 불필요하게 호출하지 않고 depends_on 사유로 안전하게 건너뜁니다.
  • 사전 스키마 감지 (Introspective Discovery): Salesforce의 경우 describeGlobal을 먼저 호출하여 해당 테넌트에 실제 설치된 220개 sObject만 선별 수집합니다.
데이터 무결성 및 내결함성
  • 0-Failed 무장애 보장 (Graceful Optional Fallback): 기업마다 다른 플랜(Plan)이나 선택적 권한으로 인해 403이 발생할 수 있는 호출은 api.optional로 격리되어 전체 수집 파이프라인의 중단을 방지합니다.
  • 멀티 테넌트 격리: 모든 수집 데이터는 run_id와 타임스탬프 기반으로 격리 저장되며, 이전 SaaS의 수집본과 결합(Merge)되어 통합 스냅샷으로 게시됩니다.
  • SQLite 로컬 캐시 및 SQLite WAL: 외부 고비용 DB 설치 없이 경량 SQLite 단일 파일로 2,000여 개 이상의 객체 관계 그래프를 밀리초 단위로 쿼리합니다.

3. 데이터 수집 시 안전성 및 개인정보 보호 설계 원칙

AEGI 수집기는 보안 감사를 수행하는 도구 자체가 새로운 보안 취약점이 되지 않도록 철저한 보안 안전 장치(Security Controls)를 준수합니다.

Privacy Protection
본문 데이터 원천 비수집

이메일 본문, 슬랙 대화 내용, 소스코드 본문, 드라이브 문서 내용을 절대 수집하지 않습니다. content_bearing_endpoint 필터를 통해 메타데이터와 접근 제어 설정만 수집합니다.

Credential Masking
비밀값 마스킹 & 해시 지문

API 토큰, OAuth Client Secret, 개인키, Webhook 시크릿의 원본 문자열은 메모리에서 즉시 마스킹 처리되며, 오직 자격증명의 존재 여부와 식별을 위한 SHA-256 지문(Fingerprint)만 저장합니다.

Least Privilege
읽기 전용 최소 권한 원칙

모든 SaaS 어댑터는 쓰기(Write) 권한을 요구하지 않습니다. OAuth 스코프는 .readonly 또는 read 계열만을 요청하여 고객사 테넌트의 기존 구성을 절대 변경하지 않습니다.

4. 6대 SaaS별 연동 명세 (우선순위, 권한, 단계별 절차, 현황)

4.1 GitHub (Organization & Enterprise)

Full 59 · Partial 31 · Failed 0 · Skipped 1

GitHub 어댑터는 소스코드 저장소, 브랜치 보호 규칙, 배포 환경, GitHub Actions 워크플로, App 설치 현황, 그리고 조직/엔터프라이즈 감사 로그를 수집합니다.

1. 지원하는 연동 방식 및 우선순위

  1. 1순위 (기본 탭 PAT): Personal Access Token (GITHUB_OWNER_TOKEN) — 대시보드 GitHub 연결 창에서 먼저 열리는 방식. Enterprise Owner Classic PAT이면 엔터프라이즈 SAML 매핑(GH-20) 및 전사 감사로그(GH-19)까지 연동.
  2. 2순위 (자체 GitHub App · Manifest): 대시보드 [새 GitHub App 생성 (Manifest)] 버튼으로 사내 전용 GitHub App을 생성하면 App ID와 개인키(PEM)가 로컬에 자동 저장되며, 조직에 설치 시 자동 연동됩니다.
  3. 3순위 (대안): 자체 OAuth App 로그인 — 사내 GitHub OAuth App의 Client ID·Secret을 입력해 사용자 OAuth 토큰 발급.

2. 필요한 계정 역할 및 권한 (Scope) 명세

구분 표준 권장 계정 및 필요 권한
계정 역할 Organization Owner (조직 소유자)
(엔터프라이즈 전사 수집 시: Enterprise Owner 겸임)
App 권한
(모두 Read-only)		 • Repository: Contents, Metadata, Actions, Pull requests, Administration, Webhooks
• Organization: Members, Administration, Personal access tokens, Secrets, Webhooks, Teams
• Enterprise: Enterprise people, Enterprise audit log
소유자 PAT 권한 admin:org, read:audit_log, read:enterprise, repo

3. 연결하는 구체적인 순서 (Step-by-Step)

  1. 브라우저에서 조직 소유자(Organization Owner) 계정으로 로그인합니다.
  2. 대시보드 Adapters > GitHub > [자격증명 직접 입력] 탭에서 [새 GitHub App 생성 (Manifest)]을 눌러 사내 전용 App을 생성합니다.
  3. 생성 완료 화면의 [조직에 앱 설치하기]를 눌러 수집할 조직을 선택합니다.
  4. 저장소 접근 범위에서 `All repositories`(모든 저장소)를 선택하고 [Install]을 클릭합니다.
  5. 로컬 서버(http://127.0.0.1:5199/__aegi/oauth/callback)로 자동 복귀되며, GITHUB_APP_INSTALLATION_ID가 .env에 자동 등록됩니다.

4. 현재 구현 현황 및 한계점 / 유의사항

  • 정상 스킵 (1건): GH-30(배포 브랜치 정책) — 저장소에 GitHub Actions 배포 환경(Environments)이 아직 생성되지 않아 정상 스킵.
  • 아키텍처 유의점: GitHub 플랫폼 보안 규정상, Enterprise App이라 하더라도 하위 Organization의 소스코드 접근은 각 조직(Org)의 소유자(Org Owner)가 App 설치를 승인해야만 열립니다.

4.2 Google Workspace (GWS)

Full 21 · Partial 7 · Failed 0 · Skipped 33

Google Workspace 어댑터는 사용자 디렉터리, 2단계 인증 강제화 여부, 외부 공유 드라이브 파일 권한, 그룹 설정, 관리자 감사 로그, OAuth 토큰 발급 내역을 수집합니다.

1. 지원하는 연동 방식 및 우선순위

  1. 1순위 (전체 수집 · 권장): 서비스 계정 JSON 키 + 도메인 전체 위임 (Domain-Wide Delegation, DWD) — 관리자 콘솔에서 스코프를 일괄 인가하여 백그라운드 무인 수집.
  2. 2순위 (빠른 연결): 관리자 OAuth 2.0 1-Click — 최고 관리자 계정의 동의 화면을 통해 15개 기본 스코프 즉시 발급.

2. 필요한 계정 역할 및 권한 (Scope) 명세

구분 표준 권장 계정 및 필요 권한
계정 역할 Google Workspace 최고 관리자 (Super Administrator)
관리자 DWD Scopes
(기본 15개)		 admin.directory.customer.readonly, admin.directory.user.readonly, admin.directory.user.security, admin.directory.group.readonly, admin.directory.rolemanagement.readonly, admin.reports.audit.readonly, drive.metadata.readonly, drive.readonly, apps.groups.settings 등
보안 확장 Scopes
(선택 추가 3개)		 • gmail.settings.basic (Gmail 자동 전달 및 외부 메일 유출 점검)
• script.deployments.readonly (Apps Script 퍼블릭 웹앱 노출 점검)
• calendar.acls.readonly (캘린더 외부 공개 ACL 점검)

3. 연결하는 구체적인 순서 (Step-by-Step)

  1. GCP 콘솔에서 서비스 계정 생성 후 키(JSON)를 다운로드합니다.
  2. Google 관리 콘솔 접속: admin.google.com (최고 관리자 계정 로그인).
  3. 보안 > 액세스 및 데이터 제어 > API 제어 > 도메인 전체 위임(Domain-wide Delegation) 메뉴로 이동합니다.
  4. [새로 추가]를 누르고, 서비스 계정의 OAuth 2 Client ID를 입력합니다.
  5. OAuth 범위 필드에 위 15개 스코프 URL 목록을 쉼표로 구분하여 등록하고 [승인]을 클릭합니다.
  6. .env 파일에 GWS_ADMIN_SUBJECT(최고 관리자 이메일) 및 GWS_COLLECTOR_SA_KEY_FILE 경로를 지정합니다.

4. 현재 구현 현황 및 한계점 / 유의사항

  • 정상 스킵 (33건): 사내에 크롬북 기기나 Chrome Enterprise 중앙 관리 브라우저가 없는 경우 chrome.management.*(12건) 등 하드웨어 전용 API는 스킵되는 것이 설계상 정상입니다.
  • 안전장치: 메일 본문(`gmail.readonly`)은 개인정보 침해 방지를 위해 의도적으로 차단되어 있으며, 자동 전달 설정(`gmail.settings.basic`)만 선택 수집합니다.

4.3 Slack (Enterprise Grid & Workspace)

Slack 어댑터는 채널 목록(공개/비공개), 멤버 권한, 설치된 서드파티 앱, Slack Connect 외부 공유 채널, 조직 감사 로그(Audit Logs)를 수집합니다.

1. 지원하는 연동 방식 및 우선순위

  1. 1순위 (원클릭): Slack 공개 배포 앱 OAuth 2.0 연동 (User Token xoxp- + Bot Token xoxb- 자동 교환).
  2. 2순위 (대안): Slack App Manifest JSON 등록 — YAML/JSON 매니페스트를 붙여넣어 수동 생성 후 토큰 발급.

2. 필요한 계정 역할 및 권한 (Scope) 명세

구분 표준 권장 계정 및 필요 권한
계정 역할 Primary Workspace Owner (기본 워크스페이스 소유자)
(Enterprise Grid 환경: Org Owner 겸임)
Bot Scopes (7개) channels:read, groups:read, team:read, users:read, usergroups:read, channels:history, groups:history
Grid Admin Scopes admin, admin.users:read, admin.teams:read, admin.apps:read, auditlogs:read

3. 연결하는 구체적인 순서 (Step-by-Step)

  1. 대시보드 Slack 연결 화면에서 [OAuth 1-클릭으로 연결 시작] 버튼 클릭.
  2. 열리는 Slack 인증 창에서 대상 워크스페이스 선택 후 [허용] 클릭.
  3. (Enterprise Grid 환경 필수) api.slack.com/apps 접속 > 앱 선택 > [Deploy to Workspaces] 메뉴에서 사용할 워크스페이스 체크 후 Deploy 클릭.

4. 현재 구현 현황 및 한계점 / 유의사항

  • 자체 복구 패치 (Auto-Discovery): Enterprise Grid 설치 시 워크스페이스 미지정으로 발생하던 team_access_not_granted 오류를 수집 엔진이 첫 단계(admin.teams.list)에서 기본 워크스페이스를 자동 탐색하여 Fallback하도록 개선 완료.
  • 정상 스킵 (4건): 워크스페이스에 생성된 유저그룹(Usergroup) 및 봇이 0개여서 하위 멤버 조회가 정상 스킵됨.

4.4 Atlassian (Jira & Confluence Cloud)

Full 12 · Partial 13 · Failed 0 · Skipped 34

Atlassian 어댑터는 Jira 프로젝트, 글로벌 권한 스킴, 역할 배정, 필터 공개 설정, Automation 규칙, Confluence 스페이스 권한, 그리고 사이트 감사 로그를 수집합니다.

1. 지원하는 연동 방식 및 우선순위

  1. 1순위 (기본 탭 개인 API 토큰): 사이트 API Token (Basic Auth) — 대시보드 Atlassian 연결 창의 「개인 API 토큰 (권장)」 탭. id.atlassian.com에서 발급받은 Unscoped API 토큰 사용. 토큰이 있으면 수집기는 OAuth 갱신 토큰보다 이 토큰을 먼저 사용.
  2. 2순위 (OAuth 탭 3LO 앱): Atlassian OAuth 2.0 (3LO) 원클릭 앱 — 사이트 선택 화면을 거쳐 갱신 토큰을 발급받아 동적 인증.
  3. 보조 (조직 감사 전용): Atlassian Guard Organization API Key — 조직 전사 감사 로그(AT-90) 수집 시 사용.

2. 필요한 계정 역할 및 권한 (Scope) 명세

구분 표준 권장 계정 및 필요 권한
계정 역할 Jira Administrators (Administer Jira 글로벌 권한) + Site Admin
3LO Scopes (6개) read:jira-work, read:jira-user, manage:jira-configuration, read:space:confluence, read:space-details:confluence, offline_access
Org API Key Scope read:events:admin (Organization Admin 권한)

3. 연결하는 구체적인 순서 (Step-by-Step)

  1. 대시보드 Atlassian 연결 화면에서 [계정 연결] 클릭.
  2. Atlassian 계정 로그인 후 권한 허용 화면에서 대상 사이트(예: 회사이름.atlassian.net) 선택.
  3. [Accept] 클릭 시 로컬 콜백으로 리다이렉트되며 ATLASSIAN_COLLECTOR_REFRESH_TOKEN 자동 저장.

4. 현재 구현 현황 및 한계점 / 유의사항

  • 최근 개선: 카탈로그 API(apiList.ts) 호출 시 기존 Basic Auth 하드코딩으로 인한 401 오류를 atlassianAuth(ctx) 동적 3LO 토큰으로 전면 교체하여 0-Failed 달성.
  • 정상 스킵 (34건): Atlassian Guard 전용 조직 감사로그(AT-90, 1건) 및 Jira 내부 세부 설정 후보 API의 권한 서킷 브레이커(28건).

4.5 Salesforce (CRM & Platform)

Full 220 · Partial 3 · Failed 0 · Skipped 295

Salesforce 어댑터는 사용자, 프로필(Profile), 권한셋(Permission Set), 역할 계층(Role Hierarchy), 비밀번호 정책, SSO 설정, 세션 설정, 그리고 220여 개 표준/커스텀 sObject 보안 설정을 SOQL로 수집합니다.

1. 지원하는 연동 방식 및 우선순위

  1. 1순위 (추천 · 원클릭): OAuth 2.0 Web Server Flow (PKCE) — Connected App을 통한 관리자 브라우저 원클릭 인증 및 갱신 토큰 보관.
  2. 2순위 (무인 서비스): Client Credentials Flow (External Client App, ECA) — 통합 사용자(Run As)를 지정하여 백그라운드 수집.

2. 필요한 계정 역할 및 권한 (Scope) 명세

구분 표준 권장 계정 및 필요 권한
계정 프로필 System Administrator (시스템 관리자) 또는 View All Data + API Enabled 보유 계정
OAuth Scopes (2개) • api (Manage user data via APIs)
• refresh_token (Perform requests at any time / offline_access)
필수 시스템 권한 View Setup and Configuration, View All Users, View Roles and Role Hierarchy, View All Profiles

3. 연결하는 구체적인 순서 (Step-by-Step)

  1. 대시보드 Salesforce 연결에서 [계정 연결] 버튼 클릭.
  2. Salesforce 로그인 페이지에서 관리자 계정 로그인 및 API 접근 [Allow] 클릭.
  3. 로컬 콜백(http://localhost:5199/__aegi/oauth/callback)으로 복귀되며 SALESFORCE_COLLECTOR_REFRESH_TOKEN 및 SALESFORCE_INSTANCE_URL 자동 저장.

4. 현재 구현 현황 및 한계점 / 유의사항

  • 정상 스킵 (295건): object_not_in_org 사유 — 현재 조직에 미설치된 OmniStudio, Devops Center, B2B Commerce 등 애드온 패키지 sObject 295개를 사전에 식별하여 불필요한 404 호출 없이 정상 필터링.
  • 성능 최적화: 토큰 자동 재발급 캐싱을 적용하여 수집 도중 세션 만료 없이 대규모 SOQL 쿼리를 연속 처리합니다.

4.6 Okta (Workforce Identity Cloud)

Okta 어댑터는 사용자, 그룹 배정, MFA 팩터 등록 현황, 등록된 애플리케이션(SAML/OIDC), 인증 정책(Sign-on Policy), 관리자 역할, 시스템 감사 로그를 수집합니다.

1. 지원하는 연동 방식 및 우선순위

  1. 1순위 (표준 권장): Okta SSWS API Token — Super Admin 콘솔에서 직접 발급하여 OKTA_API_TOKEN에 입력 (전체 관리자 API 즉시 열람).
  2. 2순위 (OAuth App): API Services OAuth App (DPoP / Private Key JWT) — 공개키 기반 서명 인증 (기업 보안 규정 준수).

2. 필요한 계정 역할 및 권한 (Scope) 명세

API Scopes
(API Services 사용 시)		 okta.users.read, okta.groups.read, okta.apps.read, okta.roles.read, okta.logs.read, okta.schemas.read, okta.policies.read

3. 연결하는 구체적인 순서 (Step-by-Step)

  1. Okta 관리자 콘솔 접속 (회사이름.okta.com).
  2. Security > API > Tokens 메뉴로 이동.
  3. [Create Token] 클릭 후 이름(예: aegi-collector-token) 입력 후 발급.
  4. 생성된 토큰 값을 복사하여 AEGI 대시보드 Okta 연결 > [API 토큰 입력]란에 저장.

  • 정상 스킵 (77건): auth_failures:5 사유 — Okta Identity Governance (OIG - 접근 요청, 권한 번들, 위임) 전용 유료 추가 SKU API 76건에 대해 서킷 브레이커가 동작하여 불필요한 호출을 안전하게 방지함.
